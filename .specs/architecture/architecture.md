# System Architecture

## Overview [ARCH-002]

The SpecPilot SDD CLI is a Node.js/TypeScript CLI tool that generates specification-driven development structures for both new and existing projects. It follows a template-based approach with intelligent codebase analysis to create consistent, customizable `.specs/` directories.

Its instruction-file step appends missing mandate sections into files the user also edits, its `project.yaml` and `tasks.md` steps write `.specs/` outside the hash-checked task writer, and it never writes `SKILL.md` (rendered per project; it reports it stale and points at `add-specs`). So the page runs the command step alone: `backfillSlashCommands()` becomes callable, keeping one list of IDE signal files and one routing table for CLI and page. The Commands split reuses the same tests (folders on the way, regular file, known hash): there `From SpecPilot` is exactly what Regenerate leaves current or may replace, and a linked, edited or CRLF `specpilot-*` file shows under `Yours`. Skills have no hash list, so their `From SpecPilot` is by path only (`specpilot-project/SKILL.md`, edited or not) and Regenerate never writes one. The linked-folder guard goes into `refreshCommands()`, the shared function, not the route (Code Rule 5), so `specpilot backfill` stops creating command files through a linked `.claude/` too (the CLI part of BL-077 for this one writer; BL-077 stays open for `init`, `add-specs` and `refine --update`). Folders are made one level at a time without `recursive`, each re-checked with `lstat`, and a per-file write error is recorded as kept and the loop goes on, so a failure part-way reports what was written instead of throwing out of the run. As built: `isSpecPilotCommand()` beside `refreshCommands()` in `slashCommandGenerator.ts` decides the split with the same folder walk (`checkFolders()`); `regenerateReport()` in `specServer.ts` turns the per-IDE results into paths and the result lines, so the page shows text it does not compose; the lines go in a box above the groups, not a toast, as a run can name dozens of paths. Rejected: running all of `SpecBackfiller.backfill()` (a browser request would append to `CLAUDE.md` and four other rule files and write `project.yaml` and `tasks.md`; the developer chose commands only); a hash list for `SKILL.md` (its bytes depend on the project); a confirmation dialog (nothing the user wrote is replaced) [ARCH-004.49]
- **Local MCP Is a Second Door to the Same Guarded Functions (BL-PM-007, Spec Report 2026-10-09)** [ARCH-004.50]: `POST /mcp` lives in `specServer.ts` beside the page's routes, behind `--mcp`, and has no logic of its own: each tool calls what a page route already calls (`buildSpecsPayload()`/`readSpecs()`, `resolveAllowedPath()`, `newTaskShapeError()`/`newTask()`, `moveShapeError()`/`moveTask()`, `SpecValidator.validate(root, {fix: false})`, `backfillSlashCommands()` + `regenerateReport()`), and the writes go through the same `writeLock` (`locked(fn)` runs `fn` under it and settles with its outcome; the page's `underLock(res, fn)` is now `locked()` plus its 500 answer, so both doors share one chain and the page's behaviour is unchanged). The protocol is written by hand in a small module (`src/utils/mcpLocal.ts`: JSON-RPC parsing, `initialize`, `tools/list`, `tools/call` dispatch, results), stateless, JSON responses only, so no SDK and no schema library are added (SEC-004.4); input schemas are plain JSON Schema objects and the existing shape checks validate the arguments. The guard order is the page's (Host, Origin, token, content type, size) with one difference: `Origin` may be absent. The token is the page's per-start token; `--read-only --mcp` makes one for `/mcp` only, held in a separate variable (`mcpToken`), never assigned to `token`, because a null `token` is what removes the page's write routes, the registry and the token meta tag. The `/mcp` guard is its own function; the shared `writeAllowed()` is not loosened. The Home card is page code in `ui/app.js`, shown when the served page carries a `specpilot-mcp` meta tag (`page` or `env`; a second slot beside the token's), with its line built by `mcpConfigLine()` in `ui/route.js`; `serve.ts` has a twin of that one-line function for the terminal (the page cannot import TypeScript), and a test holds the two equal. `SPECPILOT_MCP_TOKEN` is read and checked in `serve.ts` and passed in as `mcpToken`; `SpecServer.mcpToken` exposes the token in use. Tool refusals are `ToolRefusal` throws that `answerMcp()` turns into `isError` results; anything else answers 500.
- **CLI-Side Slash Command Backfill**: `SlashCommandGenerator.resolveTarget()` (per-IDE path/frontmatter) is shared by both `generate()` (fresh scaffolding, creates missing files only, ARCH-004.41) and `refreshCommands()` (existing projects: adds missing files, replaces known SpecPilot versions, keeps everything else, ARCH-004.38); `SpecBackfiller.backfillSlashCommands()` calls `refreshCommands()` once per IDE whose signal file already exists (`CLAUDE.md`, `.cursor/rules/specpilot.mdc`, `.windsurfrules`, `.antigravity/rules.md`, `.github/copilot-instructions.md` — same 5 signals `backfillIdeFiles` already checks; plus `CODEX_INSTRUCTIONS.md` for Codex, written only by Codex init, targeting the in-repo `.codex/prompts/` copies); `BackfillResult.slashCommands: SlashCommandBackfillResult[]` (`added`, `updated`, `kept`) reported in a new "Slash commands" section in `backfill.ts` CLI output; ensures CLI-side backfill and web-app-side `slashCommandGenerator.ts` generation never drift apart since both read from the same `SLASH_COMMANDS` constant [ARCH-004.30]

## Data Flow [ARCH-006]

### Init Command Flow [ARCH-006.1]

1. User runs `specpilot init <project-name>` with parameters
2. CLI parses arguments and validates project name (allowlist regex)
3. Checks for existing .specs folder (CS-004)
4. Prompts for framework and GitHub username (used as `contributors` handle and `devPrefix` for ID namespacing)
5. Prompts for IDE/agent selection
6. Asks 4 project context questions (1 mandatory, 3 optional)
7. The core renders every file (ARCH-006.7); the Spec Generator writes the `.specs/` files, with mode-aware prompts
8. The IDE-native AI context file and the agent skill/instruction file (SKILL.md or CODEX_INSTRUCTIONS.md) are created from the same render, existing ones kept (BL-073)
9. Validator confirms structure integrity

### Add-Specs Command Flow [ARCH-006.2]

1. User runs `specpilot add-specs` in existing project
2. Project Detector scans for package.json, requirements.txt, etc.
3. Auto-detects language, framework, dependencies
4. Code Analyzer scans for TODOs, tests, components (unless --no-analysis)
5. Prompts for missing information (the questions of `addSpecsQuestions.ts`, shared with guided setup, BL-055)
6. Spec Generator creates .specs with analysis data (mode: existing), from options built by `addSpecsOptions()`
7. Reports discovered items (TODOs, tests, components)

### Refine Command Flow [ARCH-006.3]

1. User runs `specpilot refine` in project with .specs/
2. Reads current spec files (requirements.md, context.md, prompts.md)
3. Collects all pending changes into a list
4. Shows line-level diff preview (added/removed lines with context)
5. Prompts for confirmation (unless --no-prompts)
6. Writes approved changes to disk

### Backfill Command Flow [ARCH-006.4]

1. User runs `specpilot backfill` in a project that already contains `.specs/`
2. Command reads current `.specs/project/project.yaml` and `.github/copilot-instructions.md`; a `project.yaml` with no `rules` key on its js-yaml-parsed root mapping (the same test `validate` uses; `rules:` with any value counts as present) is skipped, as is one that does not parse (BL-066)
3. Compares current content against the SpecPilot-managed mandate/instruction blocks in the wording that file uses: copilot-instructions.md with a pre-2.0 verbose fingerprint against `MD_MANDATES`, otherwise against `TERSE_MD_MANDATES` (the wording `init` writes)
4. Computes only missing insertions or append operations; existing user-authored content is preserved
5. Detects which IDE-specific files exist (`.cursor/rules/specpilot.mdc`, `CLAUDE.md`, `.windsurfrules`, `.antigravity/rules.md`, `.claude/skills/specpilot-project/SKILL.md`) and checks each for missing mandate fingerprints
6. For each IDE signal present (`CLAUDE.md`, `.cursor/rules/specpilot.mdc`, `.windsurfrules`, `.antigravity/rules.md`, `.github/copilot-instructions.md`, `CODEX_INSTRUCTIONS.md`), adds missing `specpilot-*` command files, replaces those that match a known SpecPilot version, and keeps edited, CRLF and linked files (ARCH-004.38)
7. In `--dry-run`, prints the planned changes without writing
8. In write mode, applies the minimal merge/appends and prints a summary of updated, skipped, stale, and missing files; kept command files are listed with their reason and do not change the exit code (0)

### Plugin Init Flow [ARCH-006.5]

1. User installs the plugin from the community marketplace (`git-subdir`, SHA-pinned) and runs `/specpilot:init`
2. Claude asks the project-context Q&A conversationally (replacing the CLI's `inquirer` prompts — no CLI invoked)
3. Claude creates the fixed `.specs/` tree and IDE config files via permission-gated Bash file writes, using templates carried in the plugin bundle (emitted from `src/utils` at build time)
4. Claude reads the generated onboarding prompt and executes it in-session to populate spec content, then removes it — no paste-into-an-agent second step
5. `add-specs` and `migrate` follow the same in-session pattern; the eight `specpilot-*` workflow commands operate exactly as their CLI-generated counterparts (REQ-002.E.7–E.14)

### Serve Flow [ARCH-006.6]

1. User runs `specpilot serve [folders...] [--port <n>] [--poll <ms>] [--read-only] [--open]`; with no folders, the current one, which must contain `.specs/` (exit 1 otherwise) and is `realpath`-resolved since BL-067 like a named folder (so `checkOpenPath()` compares like for like; `process.cwd()` is already physical, so the startup line is unchanged). Each named folder is `realpath`-resolved and must be a directory (exit 1 naming it otherwise); one without `.specs/` is served for guided setup (BL-055); duplicates collapse
2. `startSpecServer()` listens on `127.0.0.1:<port>` (default 4321); `EADDRINUSE` → exit 1 with a message suggesting `--port`
3. The command prints `http://127.0.0.1:<port>`; with `--open`, spawns the platform opener (`open` / `xdg-open` / `cmd /c start`) on that fixed URL
4. Each request: Host check (403) → method check (405) → for `POST /api/tasks/move`, `POST /api/tasks/new` and `POST /api/commands/regenerate` (BL-PM-006), Origin, token, content type and size (403/415/413) → `/api/` routes resolve `?project=<n>` (default 0, anything but one served index → 404) → route: `/` and `/assets/*` from `ui/`; `/api/specs` walks `.specs/` and the Automation folders and returns `readSpecs()` output plus the nav tree; `/api/file?p=` runs the path guard and returns the file as `text/plain`; `/api/events` opens a server-sent-event stream (503 past 8)
5. A project's first open stream starts that project's poller; each settled change sends `event: change` with the changed paths to that project's streams only; the page re-fetches and redraws in place. A project's last stream closing stops its poller; the last stream of all stops the heartbeat
6. A move: the page POSTs `/api/tasks/move` with the token, its origin and `If-Match`; the server checks Host, Origin, token, content type and size, then `moveTask()` writes under the lock and answers with the new hash and payload; the poller's event for that write finds the same hash and causes no second redraw. A new task (BL-PM-005) runs the same way through `POST /api/tasks/new` and `newTask()`; the page then selects the returned `id` and opens the inspector on it
7. Guided setup (BL-055): for a named folder without `.specs/` the page GETs `/api/setup`, shows the questions and POSTs the answers with the token and its origin; after the same checks as a move, `setupProject()` runs under the lock (detect, analyse, generate into the marked staging folder, create each file exclusively, keep existing files outside `.specs/`, remove the staging folder) and answers with the fresh payload, the kept paths and the Codex notice if any; the page then shows the project and opens `development/onboarding.md`. At startup (not `--read-only`) `removeStaleStaging()` clears marked staging folders an interrupted setup left
8. Opening a folder from the page (BL-067): the `+` tile opens the sheet (since BL-PM-014 Home's `Open a Project Folder` or `Clone a Repository` does; the `+` tile shows Home, REQ-002.H.32), which GETs `/api/projects` (the registry, read from `~/.specpilot/projects.json`, or its refusal reason); the user types a path or clicks a remembered one and the page POSTs `/api/projects` with the token and its origin; after the same checks as a move, `checkOpenPath()` runs under the lock (`~`, absolute, `realpath`, directory, not home or a root, not already served), the folder is appended as index `n` with its own poller and stream set, the registry is re-read and rewritten (temp file, `fsync`, `rename`; refusals leave it untouched and are reported, not fixed), and the response carries `n`, project `n`'s payload and the registry; the page adds the tile and switches to `n`. `POST /api/projects/remove` edits the list only. At startup (not `--read-only`) `serve` records the command-line folders in the registry only when the file already exists, and prints one line when the file cannot be read
9. Starting a new project (BL-PM-003): `Start a New Project` on Home opens the sheet on its `New` tab, which GETs `/api/projects/new` (`init`'s questions); the page POSTs the parent, the name and the answers with the token and its origin; after the same checks as a move and the shape check, under the lock: the 20-project cap, `createProject()` (`checkOpenPath()` on the parent, `lstat` of `<parent>/<name>`, one exclusive `mkdir` when it is missing, or the empty check when it exists, then `placeGenerated()` with `initOptions(...)`: stage, create each file exclusively, roll back and remove the created folder on failure), then the tail of step 8 (payload, next index, registry); the response carries `n`, the payload, the registry, `kept` and the Codex notice, and the page opens `development/onboarding.md`. Since BL-PM-004 steps 7 and 9 start in the chat (REQ-002.H.27): the page GETs the questions with their steps, chat wording and the file lists, asks them one at a time in a thread, checks a typed name and handle with the rules it shares with the server, shows the recap and sends the same POST
10. Cloning a repository (BL-PM-002): `Clone a Repository` on Home opens the sheet on its `Clone` tab; the page POSTs `/api/projects/clone` with the URL, the parent, the name, the token and its origin; after the same checks as a move and the shape and URL checks: the clone slot (409 when one runs), `git config --get core.sshCommand` (422 when git is missing), then under the lock the cap and `reserveTarget()` (the parent through `checkOpenPath()`, the target, one exclusive `mkdir`), then outside the lock `git clone --no-recurse-submodules -- <url> <target>`, started without a shell, with the no-prompt environment and the time limit, then under the lock the tail of step 8 (payload, next index, registry); a failure, the limit or a closed connection kills git and empties the folder (removing it when the request made it); the response carries `n`, the payload and the registry, and the page switches to `n`, whose view is Tasks or, without `.specs/`, guided setup (step 7)
11. Ctrl+C: the handle's `close()` stops a running clone and removes what it downloaded (BL-PM-002), ends every stream, clears every timer and closes the listener

The concrete build step — a new `specpilot`-internal generator/npm script (e.g. `build:plugin`) that renders `plugin/commands/*.md`, `plugin/skills/`, and the manifest, extending the existing `slashCommandGenerator.ts` mechanism — is to be designed when the plugin work is scheduled (see BL-048).

### Render Flow [ARCH-006.7]

1. A caller (`init`, `add-specs`, `refine --update`, `specSetup`) builds `SpecGeneratorOptions` as before (BL-032)
2. `render()` defaults `date` to today, builds the `TemplateContext` (defaults, `projectType` from `mode`, `apiParadigm` from the framework) and, in phase 2, drops the optional fields that are empty
3. The `.specs/` renderers run in `SPEC_FILES` order (`api.yaml` skipped for `none`); the onboarding prompt is kept aside
4. The files outside `.specs/` are rendered for the IDE: the agent file or the settings pair, the AI context file, the eight command files, `.gitattributes`
5. `render()` returns `{ files, onboardingPrompt }`; nothing has been written
6. `generateSpecs()` creates the folders, writes the `.specs/` files, creates the others with `writeNew()` (kept when present), merges `.gitattributes`
7. It returns `{ onboardingPrompt, kept, appended }` exactly as before

## Assumptions [ARCH-007]

- **Node.js runtime**: Node.js >= 16 is required; the output module format is CommonJS (`"module": "commonjs"` in `tsconfig.json`) [ARCH-007.1]
- **File paths**: All file path operations use `path.join()` / `path.resolve()` to ensure cross-platform compatibility (macOS, Linux, Windows) [ARCH-007.2]
- **No network at runtime**: All templates are built-in; no HTTP calls are made during `init`, `add-specs`, or `validate`. `specpilot serve` opens a listener on the loopback interface only and makes no outbound requests; its UI loads nothing from outside the local server [ARCH-007.3]
- **Single project root**: Every command operates on a single root directory, except `specpilot serve`, which serves a list of roots given at start and appended to by `POST /api/projects` (BL-067; never removed or reordered while it runs), each treated exactly as a single root (BL-054); monorepo detection is out of scope [ARCH-007.4]
- **Write access**: The user has write permission to the target project directory; SpecPilot writes nothing outside the project directories it is run on, with one exception since BL-067: `specpilot serve` (not `--read-only`) writes the project registry `~/.specpilot/projects.json` (folder 0700, file 0600, atomic replace, created only when the first entry is written, never replaced when unreadable; REQ-002.H.18, ARCH-004.42). Every other command, and `serve`'s guided setup (whose staging folder is inside the served folder, BL-055), still writes only inside the project; `serve`'s new-project route (BL-PM-003) makes one folder, `<parent>/<name>`, where the request says, as `specpilot init --dir` makes it where the command line says, and writes only inside it; `serve`'s clone route (BL-PM-002) has the user's `git` fill one such folder, `<parent>/<name>`, and is the one place SpecPilot starts a process that uses the network (ARCH-004.44) [ARCH-007.5]
- **TypeScript compilation**: Source is compiled with `tsc` to `dist/`; the published package ships the compiled JS, not the TS source [ARCH-007.6]
- **No global state**: All generator functions are stateless and receive all inputs as parameters — safe for programmatic use [ARCH-007.7]
- **Core portability**: `src/core/` runs wherever ES2020 and Handlebars run: it uses no Node API, no network and, beyond the default `date`, no clock, so the same code renders in the CLI, in `specpilot serve`, in a browser and in a Worker once it is packaged (BL-032, REQ-002.I.2) [ARCH-007.8]
