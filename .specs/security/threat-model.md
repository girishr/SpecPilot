# Threat Model

## Overview [SEC-001.1]

This document identifies and assesses security threats relevant to the SpecPilot CLI tool. SpecPilot is an offline, file-generating CLI — it reads user input (CLI arguments, interactive prompts) and writes files to disk. Its own code makes no outbound network calls at runtime; since BL-PM-002 `specpilot serve` can run the user's `git clone` when the page asks for it, the one use of the network (SEC-002.5 m). Since BL-051, `specpilot serve` opens an HTTP listener on the loopback interface; it can move task rows (BL-053), in a named folder without `.specs/` create the files `add-specs` creates (BL-055), open another folder on request and remember it in `~/.specpilot/projects.json`, the one file SpecPilot writes outside a project (BL-067), create a new project folder on request with the files `init` writes (BL-PM-003), and clone a repository into a new folder on request by running `git` (BL-PM-002) (SEC-002.5).

The threat model focuses on four attack surfaces: **path traversal** via user-supplied names, **template injection** through the Handlebars rendering engine, **supply-chain compromise** of runtime dependencies, and **plugin distribution** (the Claude Code plugin surface — repo/account compromise, plugin dependencies, and build-generator poisoning).

## Threat Model [SEC-002]

### Path Traversal [SEC-002.1]

| Field             | Detail                                                                                                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | A user-supplied project name containing path separators (`../`, `..\\`) or special filesystem characters could cause SpecPilot to write files outside the intended project directory.                     |
| **Impact**        | High — arbitrary file overwrite on the local filesystem.                                                                                                                                                  |
| **Likelihood**    | Low — requires intentional malicious input from the local user.                                                                                                                                           |
| **Entry point**   | `specpilot init <project-name>` CLI argument; since BL-PM-003 also `name` in a `POST /api/projects/new` body, checked by the same function (SEC-002.5 l).                                                                                                                                                             |
| **Mitigation**    | Project name is validated against an allowlist regex `^[a-zA-Z0-9][a-zA-Z0-9._-]*$` before any filesystem operation (FIX-007 / CD-046). Path separators, null bytes, and special characters are rejected. |
| **Residual risk** | Minimal. The allowlist approach blocks unknown-bad characters by default rather than trying to enumerate known-bad ones.                                                                                  |

### Template Injection [SEC-002.2]

| Field             | Detail                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Description**   | User-supplied values (`projectName`, `description`, `author`) are interpolated into Handlebars templates. A crafted input could inject Handlebars expressions (`{{`, `{{{`) to execute arbitrary helpers or access prototype properties.                                                                                                                                                                     |
| **Impact**        | Medium — could produce malformed spec files or, in theory, invoke registered Handlebars helpers with attacker-controlled arguments.                                                                                                                                                                                                                                                                          |
| **Likelihood**    | Low — the allowlist regex on `projectName` blocks `{` and `}` characters; `description` and `author` are interpolated through `{{ }}` as data (HTML-encoded until BL-PM-004b, as typed since).                                                                                                                                                                                                                           |
| **Entry point**   | All fields rendered by `TemplateEngine.renderFromString()`: `projectName`, `description`, `author`, `framework`, `language`. Since BL-055 `author` (the handle), `language` and `framework` can also arrive in a `POST /api/setup` body (SEC-002.5 j). Since BL-PM-003 `projectName`, the handle, `language` and `framework` can arrive in a `POST /api/projects/new` body, under the allowlists of mitigations (1) and (5); its four project-context answers are written into `.specs/development/onboarding.md` as plain text and are never compiled as a template (SEC-002.5 l). BL-032 phase 2 adds the 23 optional fields of REQ-002.I.4, all of them context values rendered through `{{ }}` or the `yaml`/`yamlList` helpers, never template text; no command or route sends them until BL-PM-004b.                                                                                                                                                                                                                                                                                 |
| **Mitigation**    | (1) `projectName` validated by allowlist regex — `{`, `}`, and all non-alphanumeric/dot/dash/underscore characters rejected (FIX-007). (2) Values are data to Handlebars, never template source, so `{{` in a value is text; since BL-PM-004b the engine does not HTML-escape (`noEscape`, SEC-004.3 revised), as the output is Markdown and YAML. (3) No `{{{ }}}` in any template (with `noEscape` it would mean the same as `{{ }}`). (4) Only 11 safe helpers registered (`uppercase`, `lowercase`, `capitalize`, `currentDate`, `currentYear`, `join`, and since BL-032 phase 2 `any`, which tests presence, and `yaml` and `yamlList`, which quote and escape a context value for YAML, and since BL-PM-004b `dq`, which escapes `\` and `"` inside a template's double quotes, and `fm`, which quotes a front-matter value through `yamlScalar` when it holds one of the seven characters HTML escaping covered) — none execute arbitrary code, and none compiles anything. (5) Over HTTP (BL-055) the handle must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,38}$` and every other answer must be one of the fixed choices, so no `{`, quote, space or line break from a request reaches a template. |
| **Residual risk** | Low. `description`, `author`, `--lang` and `--framework` come from the terminal, and in `add-specs` (also run by `specpilot serve` on a folder or a cloned repository, BL-PM-002) the project name comes from the folder's own `package.json` or build file, not the allowlist; since BL-PM-004b these free values reach YAML only through `fm`, `dq`, `yaml` or `yamlList`, so a name such as `'q` or `a"b` still gives YAML that parses (pinned by a test). A local user who controls the terminal can already write arbitrary files. `project.yaml`'s template source is built only from a fixed table of language and framework names (`getBuiltinTemplate`); a typed `--framework` is a lookup key and never template source.                                                                                                                                                                                                                         |

### Supply Chain [SEC-002.3]

| Field             | Detail                                                                                                                                                                                                                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | A compromised or malicious version of a runtime dependency could execute arbitrary code when SpecPilot runs.                                                                                                                                                                                                                      |
| **Impact**        | Critical — full code execution in the context of the CLI process.                                                                                                                                                                                                                                                                 |
| **Likelihood**    | Very low — all dependencies are widely-used, actively maintained packages.                                                                                                                                                                                                                                                        |
| **Entry point**   | `npm install` / dependency resolution at install time.                                                                                                                                                                                                                                                                            |
| **Dependencies**  | `commander` (CLI parsing), `handlebars` (templating), `chalk` (terminal colors), `inquirer` (interactive prompts), `js-yaml` (YAML parsing in `specValidator.ts`, `init.ts` and `specServer.ts`). `fs-extra` was removed in BL-056: it was declared but never imported. |
| **Mitigation**    | (1) Minimal dependency set — 5 direct runtime dependencies, all imported; `specpilot serve` added none (`node:http` is built in). (2) `package-lock.json` pinned in the repository. (3) No network calls at runtime by SpecPilot's own code or its dependencies, so a compromised dep cannot phone home silently during normal operation; the one process that uses the network is the user's `git`, run by `specpilot serve` for a clone the page asks for (BL-PM-002, SEC-002.5 m). (4) All dependencies are high-profile packages with large install bases and active security reporting. |
| **Residual risk** | Non-zero but industry-standard. Periodic `npm audit` runs and lockfile review are recommended.                                                                                                                                                                                                                                    |

### Plugin Distribution [SEC-002.4]

Distributing SpecPilot as a Claude Code plugin (REQ-002.G, ARCH-004.27) adds a **new attack surface** distinct from the CLI. A Claude Code plugin runs with the user's privileges and is trusted on the basis of its source; Anthropic's marketplace review is a filter, not a guarantee.

| Field             | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | (a) **Repo/account compromise → auto-pin bump**: because the plugin lives in this repo and the community catalog auto-bumps the pinned commit SHA as commits are pushed, a merged malicious PR or a stolen push credential produces a new commit that becomes the installable version for new installs and for users with auto-update enabled. (b) **Plugin-dependency supply chain**: if the plugin ever shipped its own npm deps + an install hook, every such dep would run on the user's machine. (c) **Generator poisoning**: since the plugin is built from `src/utils`, a compromise of the build tooling, a template, or a generator dependency flows silently into the committed `plugin/` bundle. |
| **Impact**        | Critical — arbitrary code execution at the installing user's privilege level, on developer machines.                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Likelihood**    | Low — requires compromising the maintainer's repo/account or the build/dependency chain.                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Entry point**   | `girishr/SpecPilot` git history (`plugin/` subtree), the `build:plugin` generator and its dependencies, and the community-marketplace `git-subdir` pin.                                                                                                                                                                                                                                                                                                                                                                                        |
| **Mitigation**    | (1) **Lowest-privilege plugin**: no hooks, no MCP, no `bin/`, no monitors, no shipped npm deps — the plugin only proposes permission-gated file writes (SEC-004.5). (2) **No install hook / no runtime deps** eliminates plugin-dependency supply chain (SEC-004.7). (3) **Repo hardening**: branch protection on `main`, required review, 2FA/passkeys, and treating everything under `plugin/` and the build generator as security-sensitive in review (SEC-004.6). (4) **SHA pinning + cache-copy**: users get exactly the reviewed commit; Claude Code copies marketplace plugins to a local cache and skips symlinks pointing outside the plugin dir, blocking host-file exfiltration. (5) **Generated-not-hand-edited** bundle keeps the audited surface in `src/utils` rather than in opaque plugin files.                                     |
| **Residual risk** | Non-zero: users who enable auto-update receive a poisoned commit N+1 before manual review. Reduced by repo hardening and the no-code-execution plugin shape (worst case is permission-gated file writes the user still approves).                                                                                                                                                                                                                                                                                                               |

### Local Spec Server — `specpilot serve` [SEC-002.5]

An HTTP server on `127.0.0.1` that shows the `.specs/` and a few generated files of one project, or of each project folder named on the command line (BL-054), in the browser (BL-051) and, unless started with `--read-only`, moves task rows in `.specs/planning/tasks.md` (BL-053), sets up `.specs/` in a named folder that has none (BL-055), and opens a folder named in a request, recording it in `~/.specpilot/projects.json` (BL-067), creates a new project folder named in a request (BL-PM-003), and clones a repository named in a request into such a folder by running `git` (BL-PM-002). Any page the user has open in the same browser can send it requests.

| Field             | Detail |
| ----------------- | ------ |
| **Description**   | (a) **DNS rebinding**: a hostile site rebinds its hostname to `127.0.0.1` and reads responses as same-origin. (b) **Path traversal / symlink escape** through `/api/file?p=`, reading files outside the project or outside the allowlist (e.g. `~/.ssh`, `.env`, source). (c) **Cross-origin reads**: another origin reading the JSON or file text. (d) **Stored XSS**: spec text rendered as HTML runs script in the UI's origin. (e) **Exposure beyond the machine** if bound to a non-loopback interface. (f) **CSRF** against `POST /api/tasks/move` (and, from BL-PM-005, `POST /api/tasks/new`, which would add a row of the forger's text rather than reorder) (BL-053): a hostile page makes the browser reorder or move the user's tasks, via a form post, a `fetch` with `no-cors`, or a DNS-rebound origin. (g) **Resource exhaustion** through live reload (BL-052): many open `/api/events` streams, or a very large allowlisted tree making each poll expensive. (h) **Write integrity**: a move that corrupts or truncates `tasks.md` (crash mid-write, two writers at once, an external editor saving at the same moment, a write through a symlink). (i) **Cross-project access** (BL-054): a request for one served project reads or writes a file of another, or of a folder that was never served, through the `project` parameter. (j) **Guided setup** (BL-055), the first route that creates files: a forged request scaffolds a folder; setup replaces, appends to or merges a file the user already has; a planted symbolic link sends a write outside the served folder; text from the request ends up in a generated file; a crash or failed write leaves a half-made tree; a request makes the server wait on a terminal prompt; a request chooses which folder is set up; the startup clean-up of stale staging folders deletes something that is not SpecPilot's. (k) **Opening a folder from a request and the registry** (BL-067), the first route that takes a path from the browser and the first write outside a project: a forged request points the server at a folder the user never named (then reads its allowlisted files through the page, or moves a `tasks.md` row or scaffolds `.specs/` there with further forged requests); a request names the home folder, `/` or a huge tree; a path with `..`, a symbolic link or `~` tricks the "already served" or "not home" check; a forged request fills the registry with paths or makes it huge, or opens folders until the pollers and stream sets pin the process; a planted symbolic link at `~/.specpilot` or `projects.json` sends the registry write elsewhere; a torn or concurrent write corrupts the user's list; the server "repairs" a file it cannot parse and loses the list; the registry file leaks folder names to other local users; a registry entry (hand-edited, or planted by another process) makes the server serve a folder at startup; removing an entry deletes the folder. (l) **Starting a new project** (BL-PM-003), the first route that creates a folder and the first that writes request text other than a handle: a forged request creates folders wherever the user can write, or many of them; the name or the parent carries `..`, a separator or a link, so the folder lands somewhere else; the route writes into, replaces or empties a folder that already has content; a typo in the parent creates a chain of folders; a failed or interrupted run leaves a half-made project, or the rollback deletes something the request did not create; the project-context answers carry template syntax, line breaks or a very long text into a generated file, or plant instructions in the onboarding prompt that the user later pastes into an AI agent. (m) **Clone a repository (BL-PM-002)**: `POST /api/projects/clone` is the first route that starts a process and the first that uses the network: the URL is read by git as an option, or names a transport that runs a command or reads local files (`-u...`, `--upload-pack=...`, `ext::`, `file://`, a local path), so a forged or mistyped request runs something or copies a local repository; the URL carries a password that then shows in an error message, the process list or `.git/config`; a hostile repository uses submodules, a redirect or another transport to reach an address the user never typed; git or ssh waits for a password, a passphrase or a host-key answer nobody can give, and the request hangs; a huge or stalled download fills the disk or holds up every other write; a forged request makes the machine contact a host, or clone into a folder, of its choosing; the clean-up after a failure removes something the clone did not create; text sent by the remote host reaches the page; the cloned files are hostile content the page then shows. |
| **Impact**        | High for (a)–(c): disclosure of local file contents. Medium for (d): script in the UI's origin can read what the UI can read. Medium for (f) and (h): unwanted or lost edits to `tasks.md`, which is under version control. High for (i): the same disclosure as (b), plus edits to another project's `tasks.md`. Medium for (j): new, unwanted files in a folder the user named; High if an existing file could be changed or a write could leave the folder, which the mitigations rule out. Medium for (k): a forged open shows the user another folder's specs and lets later forged requests do there what they can do in any served project (one line of `tasks.md`, or new files where there is no `.specs/`), and a polluted recents list; Low for the registry file itself (paths only, mode 0600); High if a planted link could redirect the registry write, which the mitigations rule out. Medium for (l): new, unwanted folders that hold only generated text, each visible as a new rail tile and a registry entry; High if an existing file or folder could be changed or removed, which the mitigations rule out. For (m): High if request text could reach a shell, become a git option or pick a transport that runs a command, which the mitigations rule out; otherwise Medium: an unwanted folder holding a repository's files, shown as a new rail tile and a registry entry, and one connection to a host named in the request, made with the user's own git credentials and bounded in time. |
| **Likelihood**    | Low — requires the server to be running and the user to visit a hostile page (a–c), or a malicious string committed into the project's spec files (d). |
| **Entry point**   | HTTP requests to `127.0.0.1:<port>`: the `Host` header, the method, the path and the `p` and `project` query parameters; long-lived `/api/events` streams; `POST /api/tasks/move`, `POST /api/tasks/new` (BL-PM-005), `POST /api/setup`, `POST /api/projects`, `POST /api/projects/remove`, `POST /api/projects/new` and `POST /api/projects/clone` bodies and headers; git's error output and the files of a cloned repository (BL-PM-002); the files of a named folder that setup reads (`package.json` and the other detector inputs, the analysed tree); `~/.specpilot/projects.json` (read at startup and on each registry route); spec file text rendered by the UI. |
| **Mitigation**    | (1) Listen on `127.0.0.1` only (e). (2) `Host` must equal `127.0.0.1:<port>` or `localhost:<port>`, else 403 (a). (3) `/api/file` path allowlist, `..` / absolute / NUL rejected, no hidden or `node_modules` segment below an allowlisted folder, no symlinked folder on the way, `realpath` must stay inside the root and the allowlist, regular files only (b). (4) No CORS headers, so browsers keep cross-origin responses opaque (c). (5) The markdown renderer escapes `&<>"` before adding its own tags; `Content-Security-Policy: default-src 'self'` blocks inline and third-party script; `X-Content-Type-Options: nosniff` stops a served `.md` being run as script (d). (6) **CSRF (closed in BL-053, was deferred to Phase 3)**: per-start random 32-byte token in a meta tag, required as `X-SpecPilot-Token` and compared with `crypto.timingSafeEqual`; `Origin` must equal the page's own origin; only `application/json` (no form posts); bodies ≤ 16 KB; the Host check; `--read-only` removes the route (f). (7) `/api/events` is capped at 8 open streams (503 beyond), has the same Host check, sends only changed paths (never content), and the poller `stat()`s only files the path guard would serve, runs per project only while a stream for that project is open, and stops with that project's last one; Ctrl+C clears every timer (g). (8) Writes: a write allowlist holding only `.specs/planning/tasks.md`; `If-Match` sha256 (409, never merge); an in-process lock; temp file + `fsync` + `rename` keeping the file mode; a symlinked `tasks.md` is refused; a move only relocates one existing line, so a move cannot inject text (the one exception is `POST /api/tasks/new`, BL-PM-005: it appends one row whose description is request text, held to one line of at most 4000 Unicode code points with no control character (U+0000–U+001F, U+007F–U+009F), no unpaired surrogate, no `|` and no trailing `\`, under an ID the server assigns, SEC-004.18); the file hash is re-checked immediately before the `rename`, so an editor save that lands mid-move gets 409 instead of being overwritten; moves that cannot keep every other byte are refused (422), not approximated: a target section with no table yet, a move involving the file's last line when it has no trailing newline, and a `tasks.md` that is not valid UTF-8 (h). (9) Projects (BL-054): the list of roots comes from the command line at start and, since BL-067, grows only through `POST /api/projects` under the checks of (11), never shrinks or reorders; `project` is only an index into it (one value of decimal digits only, no sign, no leading zero, in range, else 404), the root is chosen after the Host and method checks and, for a move or a new task, after the Origin, token, content-type and size checks, so an unauthenticated request never gets an answer that depends on the project, and every guard, allowlist, hash and poller then runs against that one root as in single-project mode, so a request cannot widen what is reachable; the one route that accepts a folder path, and the one file written outside a project, are (11) (i). (10) Guided setup (BL-055): offered only for a named folder (named on the command line, or opened from the page through (11), BL-067) in which `.specs` does not exist, and the request names it by index only; `POST /api/setup` has the layers of (6) (Host, Origin, token, JSON only, ≤ 16 KB) and `--read-only` removes both setup routes; the body is a fixed set of keys, each a choice from a fixed list except the handle, which must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,38}$` or be empty (then the OS username, as in the CLI), so no free text from a request reaches a file; the generator runs with prompts off; it writes into a staging folder inside the served folder, never into the project, and each staged file is then created in place with an exclusive create (`wx`), so an existing file, folder or link at a target path is never written through: outside `.specs/` it is kept and reported, inside `.specs/` (which the precondition says is absent) it rolls the setup back; nothing is ever replaced, appended to or merged; a parent folder that is a symbolic link or not a folder is refused, so no write follows a link out of the folder; the paths that may be created are exactly the staged files of that request, the standing write allowlist stays `tasks.md` only; setup holds the same lock as moves; a failed create removes only what the request created, and the staging folder is removed in every outcome; the startup clean-up removes only a real folder named `.specpilot-setup-<12 hex>` that holds SpecPilot's marker file as a regular file, never a link, a file or an unmarked folder, and not with `--read-only` (j). (11) Opening and the registry (BL-067): `POST /api/projects` has every layer of (6) (Host, Origin, token, JSON only, ≤ 16 KB) and is absent with `--read-only`, so a page that cannot read ours cannot open a folder; the path rule lives in one function: `~` expanded against the home directory (`homeDir()`) only, then absolute (relative → 422, so nothing resolves against the server's cwd), `realpath`-resolved before every comparison (so `..`, links and `~` cannot disguise home, a root or a served folder), a directory, not the `realpath` of home, not `path.parse(p).root`, not a served root (409 with its index); the folder is not read before it is served, and once served it is one more root under the unchanged guards of (3), (8), (9) and (10), so a forged open grants no read or write a served project does not already allow; projects stay indexed and the list is append-only, so an open cannot renumber or drop a project (i); one server serves at most 20 projects (409 past that), so a forged request cannot grow pollers and stream sets without bound (g); the registry never adds a served root: reading it only lists entries, each open is a request through this same route; the registry holds paths, a time and a flag, at most 50 entries, each path ≤ 4096 characters, so the file is bounded; `~/.specpilot` must be a real folder (`lstat`, not a link) and `projects.json` a regular file (a link is refused, never followed or replaced), created with modes 0700 / 0600; writes go to a temp file in that folder, `fsync`, `rename`; a file that cannot be read or parsed is never written (refused with the reason for the run, startup prints it); the registry is re-read under the lock right before each write; removal edits the list by string match and makes no file-system call on the folder (k). (12) New project (BL-PM-003): `POST /api/projects/new` has every layer of (6) and is absent with `--read-only`; the parent passes the one path rule of (11) (`checkOpenPath()`: `~`, absolute, `realpath`, a directory, not home, not a root), its real path must have no segment named `.specs`, and the name must match `init`'s allowlist `^[a-zA-Z0-9][a-zA-Z0-9._-]*$` (SEC-002.1) and be at most 214 characters, so the target is exactly one segment below a real, resolved folder and can hold no separator, no `..` and no leading dot; the target is looked at with `lstat`: a link or a non-folder is refused, an existing folder is used only when it is empty and not served, and a missing one is created with a single non-recursive, exclusive `mkdir` (never a parent, never `recursive`); nothing that exists is overwritten, emptied or removed; the files are written by the staging and exclusive-create path of (10), unchanged, so its keep, link-check and rollback rules apply, and the rollback additionally removes the target only when this request created it and only with a non-recursive `rmdir`; every answer is a choice from a fixed list except the handle (the allowlist of (10)) and the four project-context answers, which must be single-line strings of at most 1000 characters without control characters or line separators (U+2028, U+2029 included) and are written as plain text into `.specs/development/onboarding.md` only, never compiled as a template; a request makes at most one folder, its body is ≤ 16 KB, the 20-project cap of (11) is checked before anything is created and the lock serialises requests, so there is one folder per request and every request passes the cap check first (a request that fails at the last step, the payload read, leaves its folder without taking a slot; that needs a file in a folder just created to be unreadable); the new folder then enters the server through the tail of (11); since BL-PM-004 `whatItDoes` is required only for a Greenfield request (a Brownfield one may leave the four answers out; when sent they pass the same limits), and the name and handle rules the server applies are loaded from `ui/route.js`, the file the page also runs them from: one copy, read from the server's own install folder like the rest of `ui/`, and the page's check replaces none of the server's (l). (13) Clone (BL-PM-002): `POST /api/projects/clone` has every layer of (6) and is absent with `--read-only`; git is started without a shell, as the argument array `['clone', '--no-recurse-submodules', '--', url, target]` (`spawn`, no shell option), and nothing else from the request reaches the command line; the URL passes an allowlist of three anchored forms (`https://host[:port]/path`, `ssh://[user@]host[:port]/path`, `user@host:path`) on a fixed character set, 1 to 2048 characters, no whitespace or control character, never a leading `-`, no user or password in an https URL, and is handed to git unchanged; `GIT_ALLOW_PROTOCOL=https:ssh` has git itself refuse every other transport, also after an `insteadOf` rewrite and for a local folder named like the URL (both tested; redirects by git's documented intent, not tested); no submodules; nothing can wait on a prompt: stdin closed, no controlling terminal (POSIX), `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS`, `SSH_ASKPASS_REQUIRE=never` (OpenSSH 8.4 or later), `GCM_INTERACTIVE=never`; on Windows also ssh in batch mode unless the user has an ssh command of their own; the user's ssh setup is never replaced; a 10-minute limit, after which the process group is killed; one clone at a time (409), counted toward the 20-project cap of (11), run outside the write lock so other writes are not held up, its folder, and anything inside it, reserved under the lock and refused to the open and new-project routes (409) until the request ends; no clone starts once the server is stopping (503); `GIT_DIR` and `GIT_WORK_TREE` are not passed to git; `serve` stops a running clone on SIGINT, SIGTERM and SIGHUP, waiting at most 5 seconds for the clean-up; the parent, the name and the target follow the rules of (12) through the same function, so the folder is one allowlisted segment under an existing, `realpath`-resolved parent, made by one exclusive `mkdir` or found empty; a failed, timed-out, cancelled or interrupted clone is cleaned up: only when the target is still a real folder, its entries are removed without following links, and the folder itself only when the request created it; git's message reaches the page as one line (the last `fatal:` line with the line before it, never a `remote:` line), control characters removed, at most 300 characters, shown as text; the cloned folder then enters through the tail of (11) and is read only through the guards every served folder has (b, d, i) (m). |
| **Residual risk** | Low. Any local process can already read these files directly; the server adds no capability a local user lacks. The residual browser-side risk is a renderer escaping bug, contained by the CSP. For (h): an external editor save landing in the instant between the pre-rename hash re-check and the `rename` itself would be overwritten; closing that window needs OS-level file locking, which Node does not offer portably. `tasks.md` is under git, so such a loss is recoverable. For (j): if the process is killed during the creates, some new files and a marked `.specpilot-setup-*` folder can remain; both hold only generated text and nothing pre-existing was touched; the next `serve` start removes the marked folder; if the kill landed before the `.specs/` creates, a later setup keeps the files that exist (one of which can be partly written) and creates the rest, so the user should check the kept list; if it landed during them, `.specs/` exists partially, setup is no longer offered and `add-specs` refuses too, so the user removes `.specs/` by hand. A stale staging folder that cannot be removed at startup is skipped silently and stays until the user deletes it. A folder that someone names `.specpilot-setup-<12 hex>` and plants the marker in would be removed at startup; it is inside a folder the user named, under a name and marker that are SpecPilot's. The Code Analyzer follows symlinked folders and has no file cap, exactly as under `add-specs`, but setup makes it reachable from the page: a very large named folder (e.g. `~`) blocks the server for the whole scan, and names from outside the folder can land in the generated architecture tree. A local process that swaps a parent folder for a link between the check and the create could redirect a new file; such a process can already write wherever the user can. Detector inputs (`package.json` name, description) are rendered as the CLI renders them (SEC-002.2). For (k): a forged request that passes every CSRF layer can make the server serve any folder the user can read, which the user then sees in the rail; the folder's contents are still reached only through the read allowlist and the two write routes with their rules, and the user sees the new tile and the registry entry. The write lock is per process, so two `serve` processes writing the registry at the same instant can lose one update (the window between the re-read and the `rename`); accepted by the developer: the list is a convenience, re-created by opening the folder again, and the file itself can never be corrupt or truncated because every `rename` swaps in a complete, `fsync`ed temp file, so at worst one entry is missing. A registry entry for a folder the user no longer has shows as `folder not found` and is removed by hand from the sheet, never automatically. The remembered paths tell another process with the user's rights which folders the user works on; that process could already list them. A planted link at `~/.specpilot` or `projects.json` disables the registry for the run rather than being followed. For (l): a forged request that passes every CSRF layer can create one generated project folder per request, up to the 20-project cap, in any folder the user can write to other than home and a drive root; each shows as a tile and a registry entry and holds only generated text. The context answers end up in `onboarding.md`, a file whose stated purpose is to be pasted into an AI agent, so text planted there by a forged request would read as instructions to that agent; the user would be looking at a project they did not create. A process killed during the creates leaves the new folder with some files and a marked staging folder; it is neither served nor recorded, and the startup clean-up covers only folders served at startup, so the staging folder goes when the folder is next named on the command line, or by hand. Between the `lstat` and the `mkdir` another process can create the target (the `mkdir` then fails and nothing is written); between the empty check and the creates it can add files, which the exclusive creates keep. For (m): the clone runs with the user's own git configuration, credentials and ssh keys, as `git clone` typed in a terminal does: a forged request that got past (6) could make one clone of an https or ssh URL of its choosing into a new folder under a parent of its choosing (not home, not a root), which the user sees as a new tile and a registry entry. URL rewrites, credential helpers, template hooks and filters the user has configured run as they do in a terminal; with Git LFS installed, git-lfs downloads from the address the repository names. A credential helper or a custom ssh command that opens its own window is not closed by SpecPilot; the time limit ends the wait. The limit is on time, not size: up to 10 minutes of download can be on disk before the clean-up removes it. If the `serve` process is killed outright (SIGKILL) during a clone, git, which runs in its own session, keeps running to its end with no time limit, and the folder stays as git leaves it; it is neither served nor recorded, a later clone into it is refused as not empty, and it has to be removed by hand. On Windows the kill ends git but can leave a helper process running until it ends by itself. A `fatal:` line can quote the remote host (`fatal: remote error: ...`), and the line before it can be an ssh banner the host sends; both are shown as plain text, within the 300 characters. A clean-up that takes longer than 5 seconds after a stop signal is abandoned, and the folder stays. The empty `GIT_ASKPASS` and `GCM_INTERACTIVE` settings rest on git's source and on a check by hand, not on a documented guarantee. Another local process that puts files into the reserved folder before git starts makes git fail, and the clean-up then removes those files with the rest: everything in a folder that was empty under the lock is treated as the clone's. For (f) with BL-PM-005: a forged new-task request that passed every layer would add one visible row of the forger's text, which an AI agent reading `tasks.md` would see; it is one line in a file under git, so the diff shows it and it is recoverable. BL-PM-010 and BL-PM-013 (built 2026-10-10) add a `cursor://file/` link and per-file `vscode://file/` links built the same way, and a `cursor://anysphere.cursor-deeplink/prompt?text=` link carrying the project's own `onboarding.md` prompt: still no route, process or write; the app scheme keeps the text on this machine (the `cursor.com/link/` form is not used); the server learns only whether `.cursor/rules/specpilot.mdc` exists in a served project, through the same path checks, without serving it (SEC-004.8). A project cloned from an untrusted repository (BL-PM-002) brings its own `onboarding.md`, so the prompt Cursor pre-fills, or the user copies, is that repository's text, which may try to steer the agent; Cursor shows it in the chat and runs nothing until the user confirms, and the page labels it as the project's onboarding prompt, not SpecPilot's. Since BL-PM-008 the page also shows `vscode://file/<path>` links to the project folders it already lists (REQ-002.H.31): no route, no process and no write on SpecPilot's side; the path is one the server sent, the browser opens it only on a click (and may ask first), VS Code asks again before opening a `vscode://file` link (unless `security.promptForLocalFileProtocolHandling` is off), and VS Code's Workspace Trust prompt is the guard for a folder of unknown origin, such as a clone (BL-PM-002). |

### Command File Refresh: `specpilot backfill` [SEC-002.6]

`specpilot backfill` replaces existing `specpilot-*` command files in the project when their bytes match a version SpecPilot generated (BL-058). Since BL-PM-006 the `specpilot serve` page runs the same step through `POST /api/commands/regenerate` (SEC-004.19).

| Field             | Detail |
| ----------------- | ------ |
| **Description**   | (a) **Lost user edits**: a file the user changed is replaced. (b) **Write through a link**: a command file path that is a symbolic link, so the write lands outside the project (e.g. `~/.bashrc`). (c) **Torn write**: a crash, or an editor saving at the same moment, leaves a truncated or mixed file. (d) **Writes outside the project**: e.g. the user's `~/.codex/prompts/`, or through a folder on the way that is a symbolic link (`.claude` → elsewhere). (e) **Forged request** (BL-PM-006): a hostile page makes the browser run the refresh. |
| **Impact**        | Medium for (a) and (c): lost or corrupted local work. High for (b): overwrite of an arbitrary user-writable file. |
| **Likelihood**    | Low: (b) needs a planted link in a project the user then runs `specpilot backfill` on. |
| **Entry point**   | Files under `.claude/commands/`, `.cursor/commands/`, `.windsurf/workflows/`, `.agent/workflows/`, `.github/prompts/`, `.codex/prompts/` in the project. |
| **Mitigation**    | (1) Replace only when the raw bytes hash (SHA-256) to an entry in `KNOWN_COMMAND_HASHES` for that exact target path; anything else is kept and reported (a). (2) `lstat` first: a symbolic link or other non-regular file is kept, never followed; new files are created with `wx` so an existing path or link is never written through (b). (3) Temp file in the same folder, fsync, keep mode, re-check the hash just before `rename` (c). (4) Targets are fixed relative paths under the project directory; `~/.codex` and every other path outside it are never read or written; since BL-PM-006 folders on the way are checked with `lstat` and created one level at a time without `recursive`, and a level that is a link or not a folder keeps the file; a local process racing a folder swap between check and write is the residual (d). (5) The page route has every layer of SEC-004.10, takes no text or path, and is absent with `--read-only` (e). |
| **Residual risk** | Low. A folder swapped for a link by another local process between the `lstat` and the write can redirect one write; that process already has write access to the project. A file edited back to exactly a released version's bytes is indistinguishable from an unedited one and is replaced; its content was SpecPilot's own text. |

### Shared Spec Core [SEC-002.7]

BL-032 moves the templates into `src/core/`, a pure module that phase 3 publishes as `@specpilot/spec-core` for `init.specpilot.dev` (a public browser bundle) and the MCP server there (BL-049).

| Field             | Detail |
| ----------------- | ------ |
| **Description**   | (a) **Secret in the bundle**: anything in the core ships to every browser. (b) **CSP erosion**: runtime `Handlebars.compile()` needs `new Function`, which a page can allow only with `unsafe-eval`. (c) **YAML injection**: a value with `"`, `\` or a line break inside a double-quoted YAML scalar changes the document's structure. (d) **Package supply chain**: a second published artefact with its own version and lockfile. |
| **Impact**        | High for (a) (a leaked token), medium for (b) (a weaker CSP on the web app), low for (c) (a malformed `project.yaml` or `api.yaml` in the user's own project), high for (d). |
| **Likelihood**    | Very low: the core has no configuration, reads no environment and makes no request, so there is nothing to leak; (b) and (d) arise only in phase 3; (c) only through phase 2's new fields. |
| **Entry point**   | The optional fields of REQ-002.I.4 (phase 2); the package's build and publish (phase 3). |
| **Mitigation**    | (1) Purity rule, enforced by lint and a test: no `process`, no `fs`, no import outside the folder but `handlebars` (REQ-002.I.2); nothing secret can be read, so nothing can be embedded. (2) User input is context only, never compiled as a template (SEC-002.2); the rule holds in the core by construction, since `renderFromString()` is called only on the core's own literals. (3) Every YAML value goes through `yaml`/`yamlList` (REQ-002.I.5). (4) Phase 3: templates precompiled at build so only the eval-free Handlebars runtime ships, or no Handlebars at all; an exact-version pin and lockfile for the package; a `files` whitelist; publish only on the developer's word (SEC-004.16). |
| **Residual risk** | Low. Since BL-PM-004b markdown values are written as typed (SEC-004.3 revised); a reader that renders the files as HTML must escape them, as the serve UI does. |

### Full Setup Chat (BL-PM-004b) [SEC-002.8]

The setup chat of `specpilot serve` sends 23 more answers to the two create routes, keeps unfinished setups in the browser's storage, runs the chat core in the page from a served script, and renders files through a read-only preview route (REQ-002.H.28, REQ-002.I.7). Spec Report, 2026-10-07.

| Field             | Detail |
| ----------------- | ------ |
| **Description**   | (a) **Template or YAML injection** through a new field (a value with `{{`, a `: `, a line break). (b) **Oversized bodies**: 23 fields with free entries push requests past the old 16 KB, or a crafted body is large enough to slow the render. (c) **Saved answers read by another local page**: `localStorage` is per origin, and the origin is `http://127.0.0.1:<port>`; any other server later run on that port (another tool's dev server) can read `sp-setups`. (d) **Token in storage**: a saved setup that carried the token would hand it to that other page. (e) **Served script integrity**: `/assets/chat-core.js` is built from the core and runs in the page's origin with the token in reach. (f) **Preview as a read oracle**: the preview route renders for a folder; if it took a path from the body it could probe the disk. |
| **Impact**        | High for (d) (writes with the user's token while the server runs). Medium for (a) (a broken or misleading spec file). Low for (b), (c) (project descriptions and choices, typed by the user, nothing secret by design), (e) and (f). |
| **Likelihood**    | Low: the input is the local user's own typing in their own page, already behind the Host, Origin and token checks (SEC-002.5); (c) needs another program served on the same port and origin later. |
| **Entry point**   | The 23 keys in `POST /api/projects/new` and `POST /api/setup`; `POST /api/preview`; `sp-setups` in `localStorage` (until BL-PM-016); `/assets/chat-core.js`. |
| **Mitigation**    | (1) Each field is checked at the route before the lock: type, at most 1000 or 100 characters, lists at most 25 items, integration keys from a fixed list of eight, one line, no control characters or U+2028 / U+2029 (a); values reach the templates only through `{{ }}` and the `yaml` / `yamlList` helpers (REQ-002.I.5, SEC-004.16). (2) 64 KB body limit (bytes) on the three routes, 16 KB elsewhere, checked per route; every ASCII body within the field limits fits, a near-limit non-ASCII body may get 413 (shown to the user, SEC-004.17); the render is linear in the input (b). (3) The saved setup holds only answers, a name, timestamps and flags; the token is never written to storage, and a test reads the stored JSON for the token's value (d); REQ-002.H.28 states where setups live and how to remove them (`Remove`, `Start over`) (c). (4) The script is the compiled core file, served from the package with `default-src 'self'` unchanged; it imports nothing, reads no global but its `exports`, and is checked by the purity test (e). (5) The preview takes the same body as the create (no path for a new project; the served project's index for guided setup), takes no lock and writes nothing; its only disk read is the guided-setup folder's detector and kept list, which `GET /api/setup` already does (f). |
| **Residual risk** | Low. A later program on the same port can read setups the user did not finish or remove; they hold what the user typed about a project they had not yet created. Accepted, as the web app accepts the same for its own origin. |

### Local MCP Endpoint — `specpilot serve --mcp` [SEC-002.9]

`POST /mcp` lets an AI IDE on this machine call seven tools over the page's guarded functions (BL-PM-007, REQ-002.H.33).

| Field             | Detail |
| ----------------- | ------ |
| **Description**   | (a) **Cross-site request** from a page in the user's browser to `127.0.0.1:<port>/mcp`. (b) **DNS rebinding** against `/mcp`. (c) **Token leak**: the config line, which holds the token, committed to git in `.mcp.json` or pasted elsewhere. (d) **Prompt-injected agent**: text in a spec file or elsewhere steers the IDE's agent into calling the write tools. (e) **Race** between a page write and a tool write. (f) **Read outside the allowlist** through `specpilot_read_spec`. |
| **Impact**        | Medium for (a), (c), (d): unwanted rows or moves in `tasks.md`, or refreshed unedited command files, all under version control. High for (f): disclosure of local files. Low for (e) with the lock. |
| **Likelihood**    | Low: needs `--mcp`, which is off by default; (c) needs the token while that server is still running. |
| **Entry point**   | `POST /mcp` with `--mcp`: headers (`Host`, `Origin`, `X-SpecPilot-Token`, `Content-Type`, `MCP-Protocol-Version`) and a JSON-RPC body of at most 16 KB. |
| **Mitigation**    | (1) Same listener on `127.0.0.1`, same `Host` check (b). (2) `Origin` absent or exactly the page's own; a browser request from another site always carries its `Origin` (a). (3) The per-start token, constant-time compared, checked before anything is read (a). (4) `application/json` only, so a browser cannot send it without a preflight, which is never answered with CORS headers (a). (5) Tools call only the page's guarded functions: the same read allowlist and realpath (f), the same write allowlist (`tasks.md`, `specpilot-*` command files), shape checks, `sha256` as `If-Match`, and the one write lock (d, e). (6) No tool for setup, new project, clone, opening folders or the registry. (7) `--read-only` removes the write tools. (8) The token dies with the server, so a committed config line is useless after a restart (c); a `SPECPILOT_MCP_TOKEN` the user sets lives as long as they keep it, is at least 32 characters, is never written by SpecPilot and is shown in the page and terminal only as `${SPECPILOT_MCP_TOKEN}` (c). (9) A missing or wrong token is 403, with a body naming `X-SpecPilot-Token`, and learns nothing about the projects. |
| **Residual risk** | Low. A local process can already read the token from `GET /` and call the page's routes with a forged `Origin`, so `/mcp` adds no capability a local process lacks. (d) is the IDE's to control: its own tool approval prompts and the agent's mandates; every write is one reviewable line in git. |

## Out of Scope [SEC-004]

- **OS-level permissions**: SpecPilot runs with the invoking user's permissions; filesystem sandboxing is the OS's responsibility.
- **Runtime environment hardening**: Node.js version security, container isolation, etc. are outside SpecPilot's scope.
- **Generated file security**: The `.specs/` files SpecPilot writes are plain text (Markdown/YAML). It is the user's responsibility to keep them safe (e.g., not committing secrets).
- **CI/CD pipeline security**: Downstream use of spec files in build pipelines is out of scope.
- **Compliance frameworks**: SOC2, GDPR, HIPAA, etc. are tracked in the backlog (BL-010) but not yet addressed.
