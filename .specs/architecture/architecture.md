# System Architecture

## Overview [ARCH-002]

The SpecPilot SDD CLI is a Node.js/TypeScript CLI tool that generates specification-driven development structures for both new and existing projects. It follows a template-based approach with intelligent codebase analysis to create consistent, customizable `.specs/` directories.

## Core Components [ARCH-003]

- **CLI Parser**: Command-line argument processing with Commander.js [ARCH-003.1]
- **Template Engine**: Handlebars helpers and `renderFromString()` utility [ARCH-003.2]
- **Spec Generator**: Thin coordinator that delegates to SpecFileGenerator, IdeConfigGenerator, and AgentConfigGenerator; `targetsOutsideSpecs(ide)` (BL-055) lists the project-relative files `generateSpecs()` writes outside `.specs/` for an IDE choice, composed from `IdeConfigGenerator.targets(ide)`, `AgentConfigGenerator.targets(ide)` and `SlashCommandGenerator.targets(ide)` plus `.gitattributes`; so that this is not a second copy of the routing, the AI-context file per IDE and the agent files per IDE become one table each (in `ideConfigGenerator.ts` and `agentConfigGenerator.ts`) that the write and `targets()` both read, the settings file names likewise, `targetsOutsideSpecs()` picks the generator with `AGENT_IDES` as `generateSpecs()` does, and `SlashCommandGenerator.targets()` calls `resolveTarget()`; a test asserts for each IDE that it equals what `generateSpecs()` actually writes outside `.specs/` into an empty folder, so the list cannot drift from the writes unnoticed [ARCH-003.3]
- **Spec File Generator**: Generates `.specs/` markdown and YAML files (prompts.md, README, project.yaml, etc.) [ARCH-003.3.1]
- **IDE Config Generator**: Generates workspace settings and IDE-native AI context file based on selected IDE; GitHub Copilot/Codex → `.github/copilot-instructions.md`; Cursor → `.cursor/rules/specpilot.mdc`; Windsurf → `.windsurfrules`; Antigravity → `.antigravity/rules.md`; Claude Code → `CLAUDE.md` (lean router: mandates inline + pointers to `.specs/` + reference to SKILL.md) via `generateAiContextFile()` → `generateClaudeMd()` [ARCH-003.3.2]
- **Agent Config Generator**: Generates Claude Code Skills (`.claude/skills/specpilot-project/SKILL.md`) and Codex Instructions (`CODEX_INSTRUCTIONS.md`); CLAUDE.md itself is in IdeConfigGenerator [ARCH-003.3.3]
- **Slash Command Generator**: `src/utils/slashCommandGenerator.ts` — parallel to IdeConfigGenerator; commands defined once as `{ name, description, body }` in exported `SLASH_COMMANDS` (starts empty, populated incrementally by BL-039 through BL-046), rendered per IDE via `SlashCommandGenerator.generate()`; called from `SpecGenerator.generateSpecs()` right after the AI context file is generated; the Codex copy-them-yourself text is the exported `CODEX_PROMPTS_NOTICE`, printed by `init` and `add-specs` after `generateSpecs()` (BL-055 moved it out of `generate()`, which prints nothing now) [ARCH-003.3.4]
- **Validator**: Spec file validation with cross-reference checking [ARCH-003.4]
- **Archiver**: Archives oversized `.specs/` files (`prompts.md` > 100 lines → `prompts-archive.md`; `tasks.md` Completed > 40 lines → `tasks-archive.md`); supports `--dry-run`; the tasks.md decision lives in one exported pure function, `planCompletedArchive(lines)`, which `specValidator.ts` `validateLineLimits()` also calls (ARCH-004.32); the prompts.md decision likewise lives in `planPromptsArchive(lines)`, shared with the validator (ARCH-004.37) [ARCH-003.9]
- **Migrator**: Version migration and structure updates [ARCH-003.5]
- **Project Detector**: Auto-detects language/framework from existing files [ARCH-003.6]
- **Code Analyzer**: Scans codebase for TODOs, tests, and architecture with nested folder tree display [ARCH-003.7]
- **Frameworks Utility**: Shared `getFrameworksForLanguage()` function [ARCH-003.8]
- **Spec Tree Printer**: `src/utils/specTreePrinter.ts` — hardcoded `.specs/` file list with one-line descriptions; called by `Logger.displayInitTree()` (split from `displayInitSuccess()` into `displayInitTree()` + `displayInitNextSteps()` in CD-girishr-035) [ARCH-003.10]
- **Spec Backfiller**: `src/utils/specBackfiller.ts` — non-destructively backfills missing mandates into `project.yaml`, `copilot-instructions.md`, `planning/tasks.md`, existing IDE files, and missing or outdated `specpilot-*` slash command files; fingerprint-based (copilot-instructions.md checked in the wording it has, terse by default; `project.yaml` without a `rules:` key left alone, BL-066; `tasks.md` convention line accepted as `CD-{devPrefix}-###` or `CD-<handle>-###`, no `## Multi-Dev Notes`, BL-069), file-existence-based and known-hash detection, append-only writes except a command file that is byte for byte a known SpecPilot version (ARCH-004.38); prompts for missing `devPrefix`; SKILL.md stale-detected only, not auto-patched; `--dry-run` supported [ARCH-003.11]
- **Markdown Sections**: `src/utils/markdownSections.ts` — `findSectionBounds(lines, heading, prefix = false)` returns `{ start, end }` for a `## ` section (`start` = index of the first line whose trimmed text equals `heading`, or starts with it when `prefix` is true — `archivePrompts()` needs prefix matching because real headings carry an ID suffix, e.g. `## Latest Entries [PROMPT-002]`; `end` = index of the next line whose trimmed text starts with `## `, or `lines.length`), or `null` when the heading is absent; the single TypeScript source of the "section ends at the next `## ` heading, not EOF" rule, used by `specArchiver.ts` (`archiveTasks()`, `archivePrompts()`) and `specValidator.ts` (`validateLineLimits()`); the bash copy embedded in the `specpilot-archive` slash command (`slashCommandGenerator.ts`) stays separate because it runs in the user's shell and cannot import TypeScript [ARCH-003.12]
- **Spec Reader**: `src/utils/specReader.ts` — pure, fs-free parser (no `fs`/`path` imports): input is a map of `.specs/`-relative path → file contents; output is per-file metadata (`fileID`, `version`, `lastUpdated`, `contributors`, `relatedFiles` from markdown front matter, or from leading `# key: value` comments for `.yaml` files) plus, for `planning/tasks.md`, the table rows of `## Backlog`, `## Current Sprint` (ID | Description) and `## Completed` (# | ID | Description) with cell text verbatim (outer whitespace only trimmed); section bounds via `findSectionBounds()`; no CLI caller yet (groundwork for `specpilot serve`, BL-050) and written to move into `@specpilot/spec-core` (BL-032) unchanged [ARCH-003.13]
- **Spec Server**: `src/utils/specServer.ts` — `node:http` server behind `specpilot serve` (`src/commands/serve.ts`); exports the Host check (`isAllowedHost()`), the `/api/specs` payload builder (`buildSpecsPayload()`, which walks `.specs/` and calls `readSpecs()`) `createSpecServer(roots, specpilotVersion, opts)` and `startSpecServer(roots, port, specpilotVersion, opts)`, where `roots` is the ordered list of served project folders (BL-054; one entry when no folder is named); every `/api/` route resolves `?project=<n>` to one root (for `POST /api/tasks/move`, after the Origin, token, content-type and size checks) and then runs exactly as before against that root; reads files on every request, caches nothing, writes nothing itself (Task Mover and Spec Setup do); `GET /api/events` holds the server-sent-event streams, one poller per project, starts a project's poller with its first stream and stops it with its last (the heartbeat runs while any stream is open, the 8-stream cap counts every project); `startSpecServer()` returns a handle whose `close()` ends every stream and clears every timer before closing the listener; `GET` and `POST /api/setup` (BL-055) call `specSetup.ts` (ARCH-003.20), the POST behind the same Origin, token, content-type and size checks and inside the same lock as a task move; `roots` may now hold a named folder without `.specs/`, and the server is told which roots were named on the command line. Since BL-067 `roots`, the per-project `{streams, poller}` list and the `named` flags are append-only lists the server owns: `POST /api/projects` (`handleProjectAdd`) pushes one entry to each under the write lock, after `projectRegistry.ts` (ARCH-003.21) has checked the path and the folder's payload has been built once (an unreadable folder is refused, 422, before anything is pushed), and nothing removes or reorders them; the locked part of every write route runs through `underLock()`, which answers 500 on a throw and keeps the lock chain alive; `projectIndex()` reads the live length, so a new index is valid for every route from the moment the response is sent. `GET /api/projects` and `POST /api/projects/remove` call the registry module and read nothing from any project; all three registry routes are absent with `--read-only`, like the other write routes. `opts.registry` names the registry file (the command passes `registryPath()`, `~/.specpilot/projects.json` under `homeDir()`; tests pass a path under a temp `HOME`), or is absent with `--read-only` [ARCH-003.14]
- **Serve UI**: `ui/index.html`, `ui/app.css`, `ui/md.js`, `ui/route.js` (DOM-free hash routing, incl. the optional leading project index `#<n>/`, and the "no longer exists" markup, `require`d by Jest), `ui/app.js` and `ui/favicon.svg` (the SpecPilot logo) at the package root (shipped via `package.json` `files`), ported from the approved mockup `specpilot-local.html`; no inline script or style (CSP `default-src 'self'`), no embedded data — it fetches `/api/specs` and `/api/file` and listens on `/api/events` with `EventSource`, redrawing in place on a change; renders spec files with the mockup's markdown renderer (`ui/md.js`, also `require`d by Jest); the server resolves `ui/` from its own install location (`__dirname`), never from cwd; while `/api/specs` reports `project.specs: false` the page shows the setup view (REQ-002.H.17), a form built from `GET /api/setup` with no text of its own beyond the strings that requirement lists; the `+` rail tile and the Open a Project sheet (REQ-002.H.21, BL-067) are the mockup's `#addBtn` and `#openVeil` with the Clone tab, the Browse button and the detection preview removed, listing `GET /api/projects` and posting to `POST /api/projects` and `/api/projects/remove`; on success the page appends the tile and switches to the new index with the payload the response carries, so no second fetch is needed; the Home screen (REQ-002.H.22, BL-PM-001) is one more view of the same page, client-side only: the rail logo as a button (`#homeBtn`, `hidden` in the served HTML like `#addBtn` and shown only when the token is present), the `home` view in `ui/route.js` (`resolveRoute()`'s fourth argument says whether Home is available; without it `#home` resolves to Tasks), and a list drawn by the function that draws the sheet's list from the same `GET /api/projects`, its rows posting to the same `POST /api/projects` through the function the sheet's `Open` uses; the three decisions that can be made without the DOM live in `ui/route.js` so Jest covers them: `recentHtml()` (the rows of both lists), `openOutcome()` (what an answer to `POST /api/projects` means for the page) and `reloadView()` (the view a live-reload payload forces; never one for Home); `specServer.ts` is not touched [ARCH-003.15]
- **Spec Paths**: `src/utils/specPaths.ts` — the allowlist, the path guard `resolveAllowedPath()` and `listAllowedFiles(root)` (every file a request may read: skips `node_modules` and dot-folders, stops at 2000 files, and reports folders it cannot list as unreadable rather than empty), moved out of `specServer.ts` so the server and the poller share one definition without an import cycle; the guard applies the scanner's own walk rules (no hidden or `node_modules` segment below an allowlisted folder, no symlinked folder on the way), so the files the poller watches are exactly the files `/api/file` serves (a test compares both sets over an edge-case tree) [ARCH-003.16]
- **Spec Poller**: `src/utils/specPoller.ts` — `createPoller(root, { intervalMs, settleMs, maxSettleMs, onChange })`; every tick it lists `listAllowedFiles(root)` and `stat()`s each file (mtime, size, inode), diffs against the previous snapshot, and after a change re-checks every `settleMs` until quiet (or `maxSettleMs`) before calling `onChange(paths)` once; `start()` / `stop()`; reads no file content; ENOENT on `stat` counts as a delete, EACCES keeps the last known entry, and the files of an unreadable folder keep theirs; everything runs on one chained `setTimeout`, so `stop()` clears exactly one timer [ARCH-003.17]
- **Task Mover**: `src/utils/taskMover.ts` — the only writer in a project that has `.specs/` (BL-053; guided setup, ARCH-003.20, writes only where there is none): `planMove(content, {id, toSection, toIndex})` finds rows with `taskRowLines()` — the same table walk as `readSpecs()`, whose output is unchanged, reporting line indices and the separator row — and section bounds with `findSectionBounds()`, and returns the new content (the original lines with one line removed and the identical line inserted) or a refusal; `moveTask(root, move, ifMatch)` (called with the root the request names) holds one per-process lock shared by every project, so moves in different projects also run one after another, re-reads and hashes `tasks.md`, applies `planMove`, runs the validator's `tasks.md` checks in memory before and after (`tasksChecks()`, the same helpers `specpilot validate` now calls, output unchanged), then writes a temp file in `.specs/planning/`, `fsync`s it, `chmod`s it to the original mode and `rename`s it over `tasks.md` [ARCH-003.18]
- **Add-Specs Questions**: `src/utils/addSpecsQuestions.ts` (BL-055) — the one copy of what `add-specs` asks and how its answers become generator options: the project-type, API-paradigm and IDE choice lists, the handle message, the supported languages, and `addSpecsOptions(projectDir, projectInfo, answers, analysis)`, which returns the `SpecGeneratorOptions` that `addSpecsCommand()` passed inline until now (name and description from the detector or the CLI's defaults, mode `existing`, `.specs`). `commands/add-specs.ts` imports them for its `inquirer` prompts and its `generateSpecs()` call, with terminal output unchanged; `specSetup.ts` imports the same exports. `init.ts` keeps its own lists for now (BL-075) [ARCH-003.19]
- **Spec Setup**: `src/utils/specSetup.ts` (BL-055) — guided setup behind `specpilot serve`, the writer for a named folder without `.specs/`. `setupQuestions(root)` runs the Project Detector and returns the questions of ARCH-003.19 that apply to the folder (plus the `Choose a language:` question, which the CLI takes as `--lang`) and `keep`: for each IDE choice, which of `SpecGenerator.targetsOutsideSpecs(ide)` already exist (`lstat`, anything counts); `answersShapeError(body)` checks keys, types, the fixed choices and the handle allowlist before the lock and returns a plain-words problem or null; `setupProject(root, answers)` re-checks that `.specs` is absent (`lstat`), runs the detector once and checks `language` / `framework` against it, runs the Code Analyzer, and only then makes the staging folder `.specpilot-setup-<12 hex>/` inside the folder (exclusive `mkdir`) with the marker file `.specpilot-setup` in it, calls `SpecGenerator.generateSpecs()` with `addSpecsOptions(...)`, `targetDir` set to the staging folder and prompts off, walks the staged files (marker excluded), refuses if a parent on the way is a link or not a folder, then creates each file with `wx` + `fsync` (`.specs/` last): `EEXIST` outside `.specs/` → kept, inside → roll back and 409; any other failure → roll back (`unlink`, then non-recursive `rmdir` in reverse order) and 500; the staging folder is removed in a `finally` (`fs.rmSync` recursive, which unlinks links inside and never follows them). It imports no template and builds no path list of its own for writing: the paths are whatever the generator staged. From the `.specs` re-check to the staging folder's removal it makes only synchronous `fs` calls, as `moveTask()` does (the detector, analyser and generators are synchronous bodies behind `async`, and with prompts off nothing awaits real I/O), so no other request and no SIGINT handler runs in between and the server answers nothing else while it runs; a rejection inside it must not break the lock chain for later moves. `removeStaleStaging(root)` (called by `serveCommand()` at startup, not with `--read-only`) removes each entry matching `^\.specpilot-setup-[0-9a-f]{12}$` that is a real folder containing the marker as a regular file (`fs.rmSync` recursive, links inside unlinked, never followed), skips one it cannot remove, and touches nothing else [ARCH-003.20]
- **Project Registry**: `src/utils/projectRegistry.ts` (BL-067) — the one writer outside a project (REQ-002.H.18, SEC-004.13). `homeDir()` is `HOME`, else `USERPROFILE`, else `os.homedir()`, read from `process.env` (the order libuv uses; read this way so a test's `HOME` is honoured under Jest, whose sandboxed `process.env` the native call never sees), and `registryPath(home = homeDir())` is `<home>/.specpilot/projects.json`; the server uses `homeDir()` for `~` expansion and `~/…` display too. `readRegistry(file)` returns `{entries}` for a missing file (empty), the parsed and shape-checked entries for a valid one, or `{error}` with a plain reason when `dirname(file)` exists but is not a real folder (`lstat`), the file is not a regular file, cannot be read, is not JSON or has another shape (incl. a `lastOpened` that `Date.parse` rejects and two entries with one `path`); it never writes. `writeRegistry(file, entries)` creates `dirname(file)` with mode 0700 when missing, writes `<file>.<12 hex>.tmp` with mode 0600, `fsync`s, and `rename`s it over `file`; it throws rather than write when `readRegistry` would refuse. `upsertEntry(entries, path, now)` sets `lastOpened` on the entry with that `path` or appends `{path, lastOpened: now, pinned: false}`, then applies the cap of 50 (drop the oldest unpinned `lastOpened` first, pinned last); `removeEntry(entries, path)` matches the stored string byte for byte; `sortEntries()` is the display order (pinned first, then newest first). `MAX_PROJECTS` (20) is the cap on served projects the add route enforces. `checkOpenPath(input, roots, home)` is the add route's path rule in one place: `~` expansion against `home`, `isAbsolute`, `realpath`, directory, not `home`'s realpath, not `path.parse(p).root`, not an existing root (compared by each root's `realpath`, so it holds even for a root that came in unresolved; returns the index); it returns the real path or `{status: 409 | 422, error, project?}` and makes no call but `realpath` and `stat`. Only `serve.ts` and `specServer.ts` import it; nothing in `init`, `add-specs`, `backfill` or the generators reads or writes the registry [ARCH-003.21]

## Design Decisions [ARCH-004]

- **Template Storage**: Built-in inline templates (no external template files) [ARCH-004.1]
- **Structure Flexibility**: Customizable spec folder names [ARCH-004.2]
- **Language Support**: TypeScript, JavaScript, Python, Kotlin, and Swift with framework detection [ARCH-004.3]
- **Developer Control**: Guidelines, not prescriptions [ARCH-004.4]
- **Existing Projects**: add-specs command with intelligent analysis [ARCH-004.5]
- **Folder Structure Display**: Nested tree visualization instead of flat lists [ARCH-004.5.1]
- **Metadata First**: YAML front-matter for all spec files [ARCH-004.6]
- **Git Mandates**: Explicit prompts required for all git operations [ARCH-004.7]
- **Module Split**: specGenerator.ts split into 3 focused modules (FIX-011) [ARCH-004.8]
- **Dual Onboarding**: Separate prompts for new projects (planning-first) and existing projects (codebase-analysis) [ARCH-004.9]
- **Diff Preview**: refine command shows changes and asks for confirmation before writing [ARCH-004.10]
- **Universal Copilot Instructions**: replaced by per-IDE routing (ARCH-004.11 revised) — each IDE gets its native AI context file: GitHub Copilot/Codex → `.github/copilot-instructions.md`; Cursor → `.cursor/rules/specpilot.mdc` (YAML front-matter with `alwaysApply: true`); Windsurf → `.windsurfrules`; Antigravity → `.antigravity/rules.md`; `copilot-instructions.md` is **not** generated for Cursor/Windsurf/Antigravity since those IDEs partially or incorrectly parse it [ARCH-004.11]
- **Tiered Rules**: Generated `project.yaml` used 🔴 critical / 🟡 process / 🟢 preferences tiers until 2.0.0; since CS-067 (`0584576`) it has no `rules:` section and points to the AI agent configuration file, which holds the mandates in terse wording. `backfill` and `validate` treat a missing top-level `rules:` key as that design, not as missing mandates (BL-066) [ARCH-004.12]
- **Security Documentation**: `.specs/security/` subfolder with `threat-model.md` (path traversal, template injection, supply chain) and `security-decisions.md` (ADR-style security decision log) [ARCH-004.13]
- **Spec File Archiving**: `specpilot archive` command trims growing `.specs/` files back within tighter active-file limits to keep the working copies easy to scan; archived blocks receive a timestamped header and are appended to the corresponding `-archive.md` file; `--dry-run` flag previews without writing [ARCH-004.14]
- **Post-Init Tree Display**: After `specpilot init` and `specpilot add-specs` success, `Logger.displayInitTree()` (split from `displayInitSuccess()` into `displayInitTree()` + `displayInitNextSteps()` in CD-girishr-035) renders a tree of generated `.specs/` files via the shared `SpecTreePrinter` helper, with hardcoded one-line descriptions [ARCH-004.15]
- **Security Subfolder Generation**: `specpilot init` now generates `security/threat-model.md` and `security/security-decisions.md` starter templates in every new project; both files use YAML front-matter and labelled placeholder sections; `specTreePrinter.ts` includes both in the post-init tree [ARCH-004.16]
- **Spec-First Review Gate**: generated AI instruction files (`.github/copilot-instructions.md`, `CLAUDE.md`, Cursor, Windsurf, Antigravity; `project.yaml` until 2.0.0) include a critical mandate that blocks code or non-spec edits until the AI has read relevant `.specs/` files, updated the affected specs first, produced a Spec Report, and received an explicit developer `yes, proceed` [ARCH-004.17]
- **Non-Destructive Backfills**: `specpilot backfill` detects missing mandates vs current SpecPilot version and inserts only what's absent; append-only writes preserve user-authored content; the one replacement is an unmodified generated command file (ARCH-004.38); `--dry-run` available [ARCH-004.18]
- **Archive Branch Guard**: before `specpilot archive` runs, `archiveCommand()` calls `git rev-parse --abbrev-ref HEAD`; if the branch is not `main` or `master`, a yellow warning is printed and the user is prompted `[y/N]`; declining aborts without writing files; `--force` flag skips the prompt; branch detection failure (e.g. not a git repo) is silently ignored [ARCH-004.19]
- **CLAUDE.md as Router**: when IDE = Claude Code, `generateAiContextFile()` routes to `generateClaudeMd()` which writes a project-root `CLAUDE.md`; file is intentionally lean — critical mandates inline plus ordered list of context pointers (`.specs/project/project.yaml`, `requirements.md`, `architecture.md`, `tasks.md`, `.claude/skills/specpilot-project/SKILL.md`); design follows the "router not a dumping ground" principle (BL-023); an existing file is kept, never overwritten or appended to (ARCH-004.41, BL-073); closes BL-023 and BL-028 [ARCH-004.23]
- **IDE File Backfill via Filesystem Detection**: `specpilot backfill` detects existing IDE files without an IDE-selection prompt and appends missing mandate blocks; SKILL.md stale-detected only, not auto-patched; absent files silently skipped [ARCH-004.24]
- **Migrate Is Legacy-Only**: `specpilot migrate` remains for rare old-structure conversions and should be documented as such; same-structure backfills belong to `specpilot backfill`, not `migrate` [ARCH-004.31]
- **One Completed-Archive Plan for Validator and Archiver**: `planCompletedArchive(lines)` in `specArchiver.ts` returns the line range to move out of `tasks.md` `## Completed` (plus, for a table, the header + separator lines to repeat in the archive block), or `null`; `archiveTasks()` executes it and `validateLineLimits()` warns if and only if it is non-null, so "validate warns" and "archive acts" cannot disagree (the CD-girishr-033 bug class). Section bounds come from `findSectionBounds()`. Trigger for both shapes: section lines (`end - start`) > `COMPLETED_LINE_LIMIT` (40; 25 until BL-060), one exported constant in `specArchiver.ts` that `specValidator.ts` imports for its message. **List** shape (first `/^\d+\./` line): byte-identical to before — keep the last 20 entry lines. **Table** shape (a `|` row followed by a separator row, used only when no numbered line exists): entries are the body rows; keep `min(20, max(0, 40 - overhead))` rows, where overhead = section lines that are not body rows, so the section ends at ≤ 40 lines and, with overhead ≤ 10, leaves room for at least 10 completions; move the oldest (top) rows by position. The bash `archive_tasks()` in the `specpilot-archive` slash command mirrors this line for line, including the TS section-size arithmetic [ARCH-004.32]
- **Read-Only Local Server (BL-051)**: `specpilot serve` listens on `127.0.0.1` only and never on `0.0.0.0`; a `Host` allowlist (`127.0.0.1:<port>`, `localhost:<port>`) blocks DNS rebinding; `/api/file` is a fixed path allowlist with a `realpath` re-check so a symlink cannot escape the root or the allowlist; the write routes (BL-053 task moves, BL-055 guided setup) are protected as ARCH-004.36 and ARCH-004.40 describe. Zero new dependencies: `node:http` + `node:fs` + existing `js-yaml` (project name from `project.yaml`). The server re-reads disk per request instead of caching; live reload (ARCH-004.35) tells open pages when to re-fetch [ARCH-004.33]
- **UI Shows File Text Only**: the Serve UI keeps the mockup's layout, nav, routing, keyboard nav, theme and markdown renderer, but drops every mockup element that was not file content or that implies a write: the first-run screen (BL-055 adds guided setup as a form over the CLI's own questions, ARCH-004.40, not the mockup's screen), the clone tab, Browse button and "What SpecPilot Found" preview of the open sheet (BL-067 ports the sheet's Folder tab and the "Add a project" tile, ARCH-004.42; the preview is an analysis), the All projects view, most of the Home launcher (BL-PM-001 ports its centred column, logo, heading, a shortened intro, the Open a Project Folder button, the two benefit rows whose text is true today, the Recent projects list as path, branch and last-opened time, and the server line with the real address and version, REQ-002.H.22; its "needs you" benefit row, health cards, Needs you list, Start a New Project, Clone a Repository, MCP card and sample-project link stay out), the "needs you" badges, "in sync" / "out of date" pills, the "From SpecPilot / Yours" split (no file records which files SpecPilot generated), the hand-written "What Goes In Them" mandate list, drag and `Alt`+arrow moves, New Task, Regenerate and Open-in-Editor. Board rows show the whole description (CSS line clamp, not a cut at the first clause). Four renderer fixes against the mockup, each because it changed file text on screen: `[ID]` references keep their brackets; numbered list items show the number written in the file (`<li value>`), not a renumbering; table rows split on the first N−1 pipes like `readSpecs()`; content group headers are not CSS-uppercased. Front matter is shown as its raw block, so no key is dropped. External fonts are not loaded (CSP and ARCH-007.3); the DESIGN.md font stacks fall back to system fonts [ARCH-004.34]
- **Live Reload by Polling + Server-Sent Events (BL-052)**: `stat()` polling instead of `fs.watch` (recursive watch is unreliable on Linux before Node 20, and a poll over a bounded allowlisted set costs a few dozen `stat` calls a second); inode is compared alongside mtime and size so an atomic save (temp file renamed over the original) is caught even when the size and the mtime second match; one change → a 150 ms settle loop → one event. Server-sent events rather than WebSockets: one-way, plain `GET`, no dependency, and `EventSource` reconnects by itself. Streams are capped at 8 across all projects (503 beyond); each project's poller runs only while a stream for that project is open, and the 25 s heartbeat only while any stream is open (BL-054). Events carry paths, never content, so the stream exposes nothing `/api/specs` does not. The UI adds no connection or sync indicator (content rule) [ARCH-004.35]
- **Task Moves Are Line Moves (BL-053)**: a move is one line cut and the identical line pasted, never a re-render of the table, so the diff is always exactly one line; Backlog and Current Sprint share the `ID | Description` shape and the file's own Notes keep the BL ID on a move, so no cell changes. Optimistic concurrency by `If-Match` on the file's sha256 (409 with fresh data, never a merge) plus an in-process lock; atomic replace by temp file + `fsync` + `rename`. CSRF defence is layered because the listener is reachable from any page the user visits: a per-start 32-byte token in a meta tag (not readable cross-origin), an exact `Origin` check, `application/json` only (no form posts), 16 KB bodies, and the Host check. `--read-only` removes the route, the handles and the token. The page ignores the poller's echo of its own write by comparing `tasks.sha256` [ARCH-004.36]
- **Prompts Archive Keeps the Newest, by Date (BL-061)**: `planPromptsArchive(lines)` returns the contiguous block of oldest entries to move, a refusal with a reason, or null. Order comes from the entries' own dates, not from headings or ID numbers: this repo's log runs newest first while the generated template's `## Prompt History` table is appended oldest first, and every earlier version assumed oldest-first (and, without `## Latest Entries`, archived the boilerplate after the front matter). A single inversion is refused rather than guessed around, because "which end is older" is exactly what a wrong guess destroys. `validateLineLimits()` reports the plan's refusal reason, so validate and archive agree; the bash `archive_prompts()` mirrors the plan line for line. The trigger is `PROMPTS_LINE_LIMIT` (100), exported from `specArchiver.ts` as the only TypeScript copy; `specValidator.ts` imports it for its messages (BL-065, same as `COMPLETED_LINE_LIMIT` in BL-060). `PROMPTS_KEEP_LINES` (80) and `COMPLETED_KEEP_ENTRIES` (20) are exported alongside the limits. The bash script keeps literal copies of all four, because `scripts/command-hashes.js` loads `slashCommandGenerator.ts` on its own and cannot resolve an import; a test asserts the generated script carries the archiver's four values [ARCH-004.37]
- **Command Refresh by Known Hash (BL-058)**: no generated file records that SpecPilot wrote it, so "unmodified" means the file's raw bytes hash (SHA-256) to a version a released SpecPilot generated for that target path. `KNOWN_COMMAND_HASHES: Record<targetPath, string[]>` in `slashCommandGenerator.ts` holds every such hash from v2.2.0, the first release that wrote command files, to the current source; it is regenerated by `scripts/command-hashes.js` (not shipped in the package), which transpiles `slashCommandGenerator.ts` at every release tag and at the working tree, generates all 6 IDE targets twice into different temp directories, and exits non-zero if the two runs differ (content must not depend on per-project values). `refreshCommands(projectDir, ide, dryRun)` per target: `lstat` fails → add (`wx`, never through a link); not a regular file → kept (symbolic link / not a regular file); bytes equal current content → up to date; hash known → replace with current content (temp file in the same folder, fsync, keep mode, re-check the hash, rename); CRLF → LF matches a known hash → kept (CRLF line endings); else kept (modified). Never normalises bytes it writes and never writes outside the project directory. A unit test fails when the hash of any currently generated target is missing from the manifest, so a command-body change and its manifest update land in the same commit [ARCH-004.38]
- **Many Projects, One Server, Fixed at Start (BL-054)**: `specpilot serve a b c` serves every named folder from one server and one port; the project is a `?project=<n>` index into the command-line list. Chosen over one server per folder, which needs a port per project and cannot show one rail (each page would only know its own server, and a page on one port has a different origin from the others, so the token and Origin check would have to span origins). Chosen over a registry (e.g. `~/.specpilot/projects.json`): a registry is the first SpecPilot write outside the project (against ARCH-007.5) and, to be useful, needs a route that takes a folder path from the browser, which turns the loopback listener into a way for any page that gets past the CSRF layers to point the server at any folder; the command line already names folders and costs no new write path. Both were kept for BL-067, which adds them as ARCH-004.42 describes. Each project keeps the single-project security model unchanged — its own path guard, allowlists, `tasks.md` hash and poller — so adding projects adds no new kind of route. One origin for all projects is acceptable because every project was named by the same local user at start [ARCH-004.39]
- **Guided Setup Is `add-specs` Through the Generator, Staged Then Placed (BL-055)**: a folder named on the command line that has no `.specs/` can be set up from the page. The question set is the CLI's own, served from one shared module (ARCH-003.19), run server-side; `@specpilot/spec-core` (BL-032) is not needed, because the server is Node and can call the generator as it is, and it stays deferred. `add-specs`, not `init`: the folder already exists and was named by the local user, while `init` creates `<dir>/<name>`, a path that would have to come from the browser. The generator writes straight to disk and, until BL-073, replaced or appended to some existing files (IDE settings, command files, `.gitattributes`, which it still appends to; ARCH-004.41), so setup never points it at the project: it generates into a staging folder inside the served folder, then creates each staged file in place with an exclusive create. `.specs` must not exist (precondition); a file outside `.specs/` that already exists is kept untouched and reported, so a project with its own `.gitattributes`, `CLAUDE.md` or `.vscode/settings.json` still gets its `.specs/` and whatever else is missing, and `specpilot backfill` remains the way to add SpecPilot sections to the kept instruction files. The page shows the kept list before submit from `targetsOutsideSpecs(ide)` (ARCH-003.3), the one derived path list, pinned to the generator's real output by a test; the write itself uses no list but the staged files. That gives "same bytes as the CLI" and "never change an existing file" from one generator call. The staging folder carries a marker file, and `serve` removes stale marked staging folders at startup, nothing else, so an interrupted setup leaves no clutter. The only change to the generator is that its Codex notice moved to the two commands that call it (same text, same position in their output), so the server can return it to the page on success instead of printing it in its own terminal during staging. Rejected: a staging folder under the OS temp directory (a write outside the project, against ARCH-007.5, and possibly another volume); a second, in-memory renderer returning `{path, content}` (that is BL-032); refusing the whole setup when any target exists (the first draft; it turned away most real projects); letting the page answer the CLI's overwrite / append / skip prompts (a request would then change an existing file). The folder list still comes only from the command line and no request carries a path (ARCH-004.39 unchanged); a named folder without `.specs/` used to stop startup, and the current-directory default still does. The write surface grows from one line moved in one file to new files in a folder that has no `.specs/`, plus the removal of SpecPilot's own marked staging folders at startup; it does not grow for any project that has `.specs/` [ARCH-004.40]
- **Generators Create, Never Replace, Outside `.specs/` (BL-073)**: every write the generators make outside `.specs/` goes through one helper, `writeNew(path, content)` in `ideConfigGenerator.ts`, which creates with `wx` and treats EEXIST as kept (any other error still throws); `.gitattributes` keeps its append-missing-lines path (REQ-002.B.8). `writeNew` returns false when the file was kept; each generator returns its kept paths (project-relative, in write order), and `generateSpecs()` returns `{ onboardingPrompt, kept, appended }`, `appended` being the count `generateGitAttributes()` now returns. So `kept` is what the writes found, not a prediction, and needs no pre-check. `keepReport()` in `specGenerator.ts` turns it into the kept and appended lines that `init`, `add-specs` and `refine --update` (the three callers) print. `wx` guards the file's own path only; folders on the way are still created or followed with `mkdirSync({recursive:true})`, so a symlinked `.vscode/` or `.claude/commands/` is not refused as guided setup refuses it (BL-077). The `CLAUDE.md` / `copilot-instructions.md` overwrite / append / skip prompt, its `--no-prompts` manual-merge text and the generator's `noPrompts` option are removed (the commands' `--no-prompts` flag stays: it still skips their other questions); `specpilot backfill` remains the way to add SpecPilot sections to a kept file. Guided setup is untouched: its staging folder is empty, so `writeNew` never meets an existing file there. Rejected: routing `add-specs` through guided setup's staging and placement (ARCH-004.40), which adds rollback and a race-exact `kept` list that a terminal run does not need; keeping the prompt's append choice (the developer asked for guided setup's rule, and backfill appends only what is missing) [ARCH-004.41]
- **A Registry Outside the Project, and a Route That Takes a Path (BL-067)**: the two things BL-054 and BL-055 kept out on purpose (ARCH-004.39, ARCH-007.5) come in together, each as small as it can be. The registry `~/.specpilot/projects.json` is the first file SpecPilot writes outside a project, so it holds only what the Recent projects list needs (path, last-opened time, pinned flag), is created only when the first entry is written, is written atomically (temp file, `fsync`, `rename`) with modes 0700 / 0600, and is never replaced when it cannot be read or parsed: a refused registry turns the feature off for the run with a printed reason rather than being "repaired", because the only copy of the user's list is that file. A folder named on the command line is recorded only when the file already exists, so `specpilot serve` alone never creates one. The registry never decides what is served: it is a list the user clicks, and each click is the same `POST /api/projects` as typing the path, so there is one way a folder enters the server. That route is the first to take a path from the browser; it sits behind every CSRF layer of ARCH-004.36 and adds its own rule, kept in one function (`checkOpenPath`): `~`-expanded, absolute, `realpath`-resolved, a directory, not home, not a root, not already served. What the route grants a forged request is bounded by what the server does with a served folder: read allowlisted files, move one line of its `tasks.md`, create new files there when it has no `.specs/`; the folder itself is not read before it is served, and the registry entry is a path, not content. Projects stay addressed by index and the list stays append-only for the run (an index never changes, nothing is dropped), so every BL-054 guard, hash and poller runs unchanged against the new root; one server serves at most 20 projects (`MAX_PROJECTS`), a 409 past that, because each project costs a poller and a stream set and a forged request must not be able to grow them without bound. The write lock is per process: two `serve` processes writing the registry at once can drop one entry, never corrupt the file (each `rename` swaps in a complete `fsync`ed temp file); accepted for a recents list. The Open sheet is the mockup's Folder tab without the pieces that would be a new trust surface or an analysis: no native folder picker (a local process would have to open an OS dialog from a browser request), no Clone tab (BL-PM-002: git and the network), no "What SpecPilot Found" preview (content rule). Rejected: storing the project name or branch in the registry (they are read live from the folder once it is served, and a stale copy would be shown as fact); recording every command-line folder unconditionally (plain `specpilot serve` would then write outside the project on first use, against the "created only when needed" rule); a `DELETE` method for removal (a JSON `POST` keeps the one `writeAllowed()` path and its content-type check); repairing or rewriting a corrupt registry (the user's list is the only copy); a route that accepts a relative path or resolves against the server's cwd (the page has no cwd; `~` is the one shorthand because the rail already shows roots that way); re-reading the registry on every `/api/specs` (it is needed only in the sheet, so the sheet fetches `GET /api/projects` when it opens) [ARCH-004.42]

## Data Flow [ARCH-006]

### Init Command Flow [ARCH-006.1]

1. User runs `specpilot init <project-name>` with parameters
2. CLI parses arguments and validates project name (allowlist regex)
3. Checks for existing .specs folder (CS-004)
4. Prompts for framework and GitHub username (used as `contributors` handle and `devPrefix` for ID namespacing)
5. Prompts for IDE/agent selection
6. Asks 4 project context questions (1 mandatory, 3 optional)
7. Spec File Generator creates subfolder structure with mode-aware prompts
8. IDE-native AI context file generated based on selection; agent skill/instruction file generated (SKILL.md or CODEX_INSTRUCTIONS.md)
9. Validator confirms structure integrity

### Add-Specs Command Flow [ARCH-006.2]

1. User runs `specpilot add-specs` in existing project
2. Project Detector scans for package.json, requirements.txt, etc.
3. Auto-detects language, framework, dependencies
4. Code Analyzer scans for TODOs, tests, components (unless --no-analysis)
5. Prompts for missing information (the questions of `addSpecsQuestions.ts`, shared with guided setup, BL-055)
6. Spec Generator creates .specs with analysis data (mode: existing), from options built by `addSpecsOptions()`
7. Reports discovered items (TODOs, tests, components)

### Refine Command Flow [ARCH-006.3]

1. User runs `specpilot refine` in project with .specs/
2. Reads current spec files (requirements.md, context.md, prompts.md)
3. Collects all pending changes into a list
4. Shows line-level diff preview (added/removed lines with context)
5. Prompts for confirmation (unless --no-prompts)
6. Writes approved changes to disk

### Backfill Command Flow [ARCH-006.4]

1. User runs `specpilot backfill` in a project that already contains `.specs/`
2. Command reads current `.specs/project/project.yaml` and `.github/copilot-instructions.md`; a `project.yaml` with no `rules` key on its js-yaml-parsed root mapping (the same test `validate` uses; `rules:` with any value counts as present) is skipped, as is one that does not parse (BL-066)
3. Compares current content against the SpecPilot-managed mandate/instruction blocks in the wording that file uses: copilot-instructions.md with a pre-2.0 verbose fingerprint against `MD_MANDATES`, otherwise against `TERSE_MD_MANDATES` (the wording `init` writes)
4. Computes only missing insertions or append operations; existing user-authored content is preserved
5. Detects which IDE-specific files exist (`.cursor/rules/specpilot.mdc`, `CLAUDE.md`, `.windsurfrules`, `.antigravity/rules.md`, `.claude/skills/specpilot-project/SKILL.md`) and checks each for missing mandate fingerprints
6. For each IDE signal present (`CLAUDE.md`, `.cursor/rules/specpilot.mdc`, `.windsurfrules`, `.antigravity/rules.md`, `.github/copilot-instructions.md`, `CODEX_INSTRUCTIONS.md`), adds missing `specpilot-*` command files, replaces those that match a known SpecPilot version, and keeps edited, CRLF and linked files (ARCH-004.38)
7. In `--dry-run`, prints the planned changes without writing
8. In write mode, applies the minimal merge/appends and prints a summary of updated, skipped, stale, and missing files; kept command files are listed with their reason and do not change the exit code (0)

### Plugin Init Flow [ARCH-006.5]

1. User installs the plugin from the community marketplace (`git-subdir`, SHA-pinned) and runs `/specpilot:init`
2. Claude asks the project-context Q&A conversationally (replacing the CLI's `inquirer` prompts — no CLI invoked)
3. Claude creates the fixed `.specs/` tree and IDE config files via permission-gated Bash file writes, using templates carried in the plugin bundle (emitted from `src/utils` at build time)
4. Claude reads the generated onboarding prompt and executes it in-session to populate spec content, then removes it — no paste-into-an-agent second step
5. `add-specs` and `migrate` follow the same in-session pattern; the eight `specpilot-*` workflow commands operate exactly as their CLI-generated counterparts (REQ-002.E.7–E.14)

### Serve Flow [ARCH-006.6]

1. User runs `specpilot serve [folders...] [--port <n>] [--poll <ms>] [--read-only] [--open]`; with no folders, the current one, which must contain `.specs/` (exit 1 otherwise) and is `realpath`-resolved since BL-067 like a named folder (so `checkOpenPath()` compares like for like; `process.cwd()` is already physical, so the startup line is unchanged). Each named folder is `realpath`-resolved and must be a directory (exit 1 naming it otherwise); one without `.specs/` is served for guided setup (BL-055); duplicates collapse
2. `startSpecServer()` listens on `127.0.0.1:<port>` (default 4321); `EADDRINUSE` → exit 1 with a message suggesting `--port`
3. The command prints `http://127.0.0.1:<port>`; with `--open`, spawns the platform opener (`open` / `xdg-open` / `cmd /c start`) on that fixed URL
4. Each request: Host check (403) → method check (405) → for `POST /api/tasks/move`, Origin, token, content type and size (403/415/413) → `/api/` routes resolve `?project=<n>` (default 0, anything but one served index → 404) → route: `/` and `/assets/*` from `ui/`; `/api/specs` walks `.specs/` and the Automation folders and returns `readSpecs()` output plus the nav tree; `/api/file?p=` runs the path guard and returns the file as `text/plain`; `/api/events` opens a server-sent-event stream (503 past 8)
5. A project's first open stream starts that project's poller; each settled change sends `event: change` with the changed paths to that project's streams only; the page re-fetches and redraws in place. A project's last stream closing stops its poller; the last stream of all stops the heartbeat
6. A move: the page POSTs `/api/tasks/move` with the token, its origin and `If-Match`; the server checks Host, Origin, token, content type and size, then `moveTask()` writes under the lock and answers with the new hash and payload; the poller's event for that write finds the same hash and causes no second redraw
7. Guided setup (BL-055): for a named folder without `.specs/` the page GETs `/api/setup`, shows the questions and POSTs the answers with the token and its origin; after the same checks as a move, `setupProject()` runs under the lock (detect, analyse, generate into the marked staging folder, create each file exclusively, keep existing files outside `.specs/`, remove the staging folder) and answers with the fresh payload, the kept paths and the Codex notice if any; the page then shows the project and opens `development/onboarding.md`. At startup (not `--read-only`) `removeStaleStaging()` clears marked staging folders an interrupted setup left
8. Opening a folder from the page (BL-067): the `+` tile opens the sheet, which GETs `/api/projects` (the registry, read from `~/.specpilot/projects.json`, or its refusal reason); the user types a path or clicks a remembered one and the page POSTs `/api/projects` with the token and its origin; after the same checks as a move, `checkOpenPath()` runs under the lock (`~`, absolute, `realpath`, directory, not home or a root, not already served), the folder is appended as index `n` with its own poller and stream set, the registry is re-read and rewritten (temp file, `fsync`, `rename`; refusals leave it untouched and are reported, not fixed), and the response carries `n`, project `n`'s payload and the registry; the page adds the tile and switches to `n`. `POST /api/projects/remove` edits the list only. At startup (not `--read-only`) `serve` records the command-line folders in the registry only when the file already exists, and prints one line when the file cannot be read
9. Ctrl+C: the handle's `close()` ends every stream, clears every timer and closes the listener

The concrete build step — a new `specpilot`-internal generator/npm script (e.g. `build:plugin`) that renders `plugin/commands/*.md`, `plugin/skills/`, and the manifest, extending the existing `slashCommandGenerator.ts` mechanism — is to be designed when the plugin work is scheduled (see BL-048).

## Assumptions [ARCH-007]

- **Node.js runtime**: Node.js >= 16 is required; the output module format is CommonJS (`"module": "commonjs"` in `tsconfig.json`) [ARCH-007.1]
- **File paths**: All file path operations use `path.join()` / `path.resolve()` to ensure cross-platform compatibility (macOS, Linux, Windows) [ARCH-007.2]
- **No network at runtime**: All templates are built-in; no HTTP calls are made during `init`, `add-specs`, or `validate`. `specpilot serve` opens a listener on the loopback interface only and makes no outbound requests; its UI loads nothing from outside the local server [ARCH-007.3]
- **Single project root**: Every command operates on a single root directory, except `specpilot serve`, which serves a list of roots given at start and appended to by `POST /api/projects` (BL-067; never removed or reordered while it runs), each treated exactly as a single root (BL-054); monorepo detection is out of scope [ARCH-007.4]
- **Write access**: The user has write permission to the target project directory; SpecPilot writes nothing outside the project directories it is run on, with one exception since BL-067: `specpilot serve` (not `--read-only`) writes the project registry `~/.specpilot/projects.json` (folder 0700, file 0600, atomic replace, created only when the first entry is written, never replaced when unreadable; REQ-002.H.18, ARCH-004.42). Every other command, and `serve`'s guided setup (whose staging folder is inside the served folder, BL-055), still writes only inside the project [ARCH-007.5]
- **TypeScript compilation**: Source is compiled with `tsc` to `dist/`; the published package ships the compiled JS, not the TS source [ARCH-007.6]
- **No global state**: All generator functions are stateless and receive all inputs as parameters — safe for programmatic use [ARCH-007.7]
